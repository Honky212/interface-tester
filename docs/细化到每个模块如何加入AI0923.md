## 一、总原则

这套项目的成熟点在于：

- CLI 层：命令行入口
- converters 层：外部资产转 YAML
- loader 层：YAML / 项目加载
- make 层：生成 pytest 用例
- runner 层：真正执行用例
- models 层：数据契约
- utils 层：公共工具和脱敏

因此，AI 不能直接扎到 `runner.py` 的执行主干里，否则容易破坏现有可靠性。最稳妥的方案是：

- AI 在“生成前”和“结果后”参与，“生成草稿 / 分析失败 / 生成修正建议”
- 框架在“执行中”保持最终决策权，负责“真正执行、断言、汇总、日志、判定”
- 人类负责高风险确认

也就是说：

- AI 负责“生成草稿、分析失败、给修正建议”
- interfacetester 负责“真正发请求、断言、跑用例、给结论”

## 3. models 层：增加 AI 产物的结构化 schema

### 模块
- `.venv/Lib/site-packages/interfacetester/models.py`

### 新增数据结构设计

```python
class CaseDraft(BaseModel):
    case_name: str
    base_url_env: str = "BASE_URL"
    steps: List[StepDraft] = []
    unknowns: List[UnknownField] = []


class StepDraft(BaseModel):
    name: str
    method: str
    url: str
    headers: Dict[str, str] = {}
    params: Dict[str, Any] = {}
    json: Dict[str, Any] = {}
    data: Dict[str, Any] = {}
    extract: Dict[str, str] = {}
    validate: List[AssertionDraft] = []
    depends_on_extract: List[str] = []


class AssertionDraft(BaseModel):
    comparator: str
    check: str
    expect: Any
    source_quote: str = ""
    from_doc: bool = True


class UnknownField(BaseModel):
    where: str
    why: str


class DiagnosisResult(BaseModel):
    case_name: str
    cause_type: str
    confidence: float
    evidence: List[str]
    reason: str
    suggestion: str


class FixSuggestion(BaseModel):
    case_name: str
    step_name: str
    before: str
    after: str
    reason: str
    risk: str
    requires_human_confirmation: bool = True
```

### 关键原则

- 使用 Pydantic/结构化 JSON
- `extra="forbid"`，不允许额外字段乱塞
- 断言必须带 `source_quote`，以保证文档原句可追溯
- `cause_type` 仅允许有限值，例如：
  - `缺陷`
  - `用例错误`
  - `环境问题`
  - `数据问题`
  - `未知`

### 设计理由

这一步非常关键，因为现有框架最怕的是：字段名写错、算子写错、未知字段被静默吞掉。结构化 schema 正好解决这个问题。

## 4. loader 层：增加 AI 产物的强校验

### 模块
- `.venv/Lib/site-packages/interfacetester/loader.py`

### 新增函数设计

```python
def validate_ai_generated_case(case_data: Dict) -> None:
    """检查 AI 生成的用例草稿，拒绝未知字段和非法断言"""


def warn_unknown_testcase_fields_for_ai(raw_case: Dict) -> List[str]:
    """把未知字段从 warning 升级成 failure"""


def ensure_ai_assertion_allowed(assertion: Dict) -> None:
    """确保断言算子在合法白名单内"""
```

### 关键逻辑

- 如果 AI 输出了非法 key，直接抛异常
- 如果断言算子不在白名单，直接失败
- 如果字段写错，比如 `body` vs `json`，直接失败，而不是吞掉
- 只允许“结构化、合法、已知字段的 YAML”进入执行阶段

### 关键目的

这是 AI 接入的第一道防线，解决“LLM 生成错误用例被框架静默吞掉”的问题。

## 5. make.py 层：生成期二次校验和重试修正

### 模块
- `.venv/Lib/site-packages/interfacetester/make.py`

### 新增函数设计

```python
def generate_case_from_ai_draft(draft: Dict) -> str:
    """把 AI draft 转成 YAML 用例文本"""


def validate_emitted_ai_case(case_path: str) -> None:
    """对生成出来的 YAML 做校验，确保能被框架加载"""


def repair_ai_case(draft: Dict, error_msg: str) -> Dict:
    """把 LLM 失败原因回喂，重试生成一次"""


def make_ai_case(doc_text: str, case_name: str) -> str:
    """统一入口：文档 -> draft -> YAML -> 校验"""
```

### 关键点

- `generate_case_from_ai_draft()` 只做格式转换，不做业务判定
- `validate_emitted_ai_case()` 调用现有校验机制
- `repair_ai_case()` 负责对失败进行一次重试，最多 `<= 2` 次
- 若仍失败，则不落盘只写 `needs_human_review` 记录

### 设计上要注意

这里最好不要直接调用真实 `hrun`，否则会触发真实环境副作用。先只做生成期校验。

## 三、AI 生成/分析/修复的三层伪代码落地

## 1. 生成层伪代码

```python
# 伪代码：文档 -> 草稿 -> YAML -> 校验

def make_ai_case(doc_text: str, case_name: str) -> str:
    draft = llm_generate_case(doc_text, case_name)

    # 1. schema strict validation
    case_obj = CaseDraft.model_validate(draft)

    # 2. convert to interfacetester format
    yaml_text = generate_case_yaml(case_obj)

    # 3. save temp file
    tmp_path = write_temp_yaml(yaml_text)

    # 4. framework validation
    validate_ai_generated_case(load_yaml(tmp_path))

    # 5. hmake-like validation
    validate_emitted_case(tmp_path)

    return tmp_path
```

### 设计要点

- AI 先生成 structured JSON
- 然后转成 YAML
- 然后再走框架校验
- 失败则回放重试

---

## 2. 分析层伪代码

```python
# 伪代码：summary.json + logs -> cause_type

def analyze_failure(summary_path: str, log_dir: str) -> DiagnosisResult:
    summary = load_summary_report(summary_path)
    failures = extract_failed_cases(summary)

    evidence_list = []
    for fail in failures:
        evidence = extract_failure_evidence(fail, log_dir)
        evidence_list.append(evidence)

    payload = {
        "failures": sanitize_for_ai_payload(evidence_list),
        "rules": [
            "必须给出证据",
            "只能判定: 缺陷 / 用例错误 / 环境问题 / 数据问题 / 未知",
            "无证据不得下结论",
        ],
    }

    result = llm_analyze(payload)
    diagnosis = DiagnosisResult.model_validate(result)
    return diagnosis
```

### 关键原则

- 不允许 AI 直接凭经验猜测
- 必须用失败证据推断原因
- 结论的可信度也要保留

---

## 3. 修复层伪代码

```python
# 伪代码：失败 -> 修正建议 -> 人工确认 -> 可选落地

def suggest_fix(failure_payload: dict) -> FixSuggestion:
    payload = sanitize_for_ai_payload(failure_payload)
    fix = llm_suggest_fix(payload)
    suggestion = FixSuggestion.model_validate(fix)
    return suggestion


# 人工确认后

def apply_fix_to_case(case_path: str, suggestion: FixSuggestion) -> None:
    if not suggestion.requires_human_confirmation:
        patch_yaml(case_path, suggestion.before, suggestion.after)
    else:
        print("等待人工确认后再修改")
```

### 设计原则

- 默认只输出建议，不直接执行
- 仅在低风险场景才允许自动落地
- 人工确认必须在命令行或界面上显式确认

## 五、工程落地时的最终原则

1. 不让大模型直接写 core 执行代码
2. 让 AI 只在生成、分析、修正建议环节参与
3. 用 schema + loader + make 约束 AI 输出
4. 用 runner + summary.json 做证据分析
5. 用人类进行高风险确认
6. 对所有 AI 产物保留审计日志和可回滚机会

## 推荐的最稳妥实现顺序
第一批（最值得做）
文档转 YAML 的生成器
strict schema 校验
失败证据提取
分析器
人工确认修正
第二批
AI 修正建议 diff
低风险自动修正
报告摘要生成
第三批
自动测试数据生成
debugtalk 自动生成
回归优先级推荐

---

## 六、一句话总结

“AI 接入 interfacetester 的正确落点，不是替换执行器，而是插在生成、分析和修正建议这三层，且必须由模型校验 + 框架校验 + 人工确认共同守门。”
