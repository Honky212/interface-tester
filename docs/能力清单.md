# InterfaceTester 能力清单

> 这份清单回答一个问题：**现在这套框架能做哪些接口测试自动化、哪些做不了、做不了的要花多大代价**。
> 内容基于逐文件核对源码（`interfacetester/` 全部 25 个文件）+ 仓库内已有用例/测试的实跑结果。
>
> - 版本：`interfacetester 5.0.1`
> - 最后核对：0916-8 批次修复之后
> - 与 `docs/能力边界.txt` 的关系：那份文档是**结论**（能不能投产后），本文是**清单**（逐项能力 + 依据 + 验证状态）
>
> **验证状态口径**：
> - ✅ **已验证** = 仓库内有跑通的用例/测试（`examples/`、`tests/`），且本次核对时实际跑过
> - 🟡 **可用未覆盖** = 代码路径明确支持，但没有对应用例（用之前建议先自己验一次）
> - ⚠️ **有限制** = 能用，但有明确前提或已知缺陷
> - ❌ **不支持** = 需要改框架，或根本不在本工具范围

---

## 一、一句话定位

**YAML/JSON 用例 → 自动转成 pytest 用例 → 用 requests 发真实 HTTP 请求 → 提取 + 断言 → 报告/日志**。
核心场景是 **HTTP/HTTPS 接口功能自动化**；SQL 查询校验是内置的可选扩展，Thrift 是实验性扩展。

---

## 二、能力总览

| 层级 | 含义 | 典型能力 |
| --- | --- | --- |
| **A. 开箱即用** | 写 YAML 就能跑，不用写代码、不用改框架 | HTTP 全方法、JSON/表单/上传、变量与函数、提取与断言、数据驱动、用例引用、hooks、OAuth2、多环境、报告日志 |
| **B. 写 `debugtalk.py` 就能做** | 框架不内置，但机制支持（`${func()}` 可调用任意 Python） | 签名/加密、其他认证、复杂断言、动态造数、回调验证 |
| **C. 需要改框架** | 改源码才能支持 | gRPC / WebSocket / MQ / 私有 TCP、Thrift（现状实验性）、并发与报告聚合 |
| **D. 明确不适合** | 不是这个工具的目标 | 性能压测、UI 自动化、移动端原生 |

## 三、能力明细

### 3.1 协议与请求（A）

| 能力 | 依据 | 状态 |
| --- | --- | --- |
| HTTP/HTTPS 全部方法：GET / POST / PUT / DELETE / PATCH / HEAD / OPTIONS | `models.MethodEnum` | ✅ `examples/` 有 |
| JSON 请求体（`json`）、表单/文本（`data`）、URL 参数（`params`）、请求头（`headers`）、Cookie（`cookies`） | `models.TRequest` | ✅ 0919-30 / M14：**`json:` 也接受裸标量**（`123` / `true` / `1.5` / 显式 `null`）—— 合法 JSON 的顶层可以是任意值（RFC 8259）。修复前的联合类型只有 `dict/list/str`，`json: 123` 在**加载期**就抛 `ValidationError: 3 validation errors for TRequest`。`bool` 必须在联合类型里（否则 `true` 会被静默记成 `1`）；**不含 `bytes`**（`json=` 走 `json.dumps`，要发二进制用 `data:`；pydantic 的 lax 模式会把 bytes 解成 str，属既有行为） |
| 文件上传（multipart，UTF-8 安全，中文文件名不报 `UnicodeEncodeError`） | `ext/uploader.Utf8MultipartEncoder` | ✅ `examples/httpbin/upload.yml`；**批次 C / L14**：① multipart 头参数（字段名/文件名/mime）里的 `"`/CR/LF 现在**会转义**成 `%22/%0D/%0A`（与 urllib3 逐字对齐）—— 修复前 f-string 直接插入，字段名里的换行会把头**拆行**、文件名里的 `\r\n` 能在请求体内**伪造出一行头**；② 编码器改成**流式**（片段列表 + 按需 `read()`，文件只留路径、长度用 `os.path.getsize`）—— 修复前整包先 materialize 且文件先读成 bytes，上传 N 字节的峰值内存约 **2N**（32 MB 文件实测 68 MB），与「大文件 multipart」的定位不符；现在同一操作峰值 ≈ 一个读块（实测 0.13 MB）。`.body` 属性保留（会 materialize，仅兼容既有调用方）。<br>**0920 批次 6 / N37**：上传扩展的**硬前置只剩 `filetype`** —— `requests_toolbelt` 在 L14 之后**从未被使用**（全文只有注释），此前却与 `filetype` 写在同一个 `try` 里，任一缺失就把 `UPLOAD_READY` 打成 False，于是"装了 filetype、编码器完全可用"也照样 `RuntimeError`。现在它是可选依赖（存在就 import，缺失不影响可用性） |
| URL 拼接：绝对 URL 直接用，相对路径自动拼 `config.base_url`（带路径前缀也对） | `parser.build_url` | ✅ ；**0920 批次 6 / N38**：`base_url` 自带的**查询串**不再被丢弃（网关类 `?sig=` / `?tenant=` 参数写在那里很常见）。口径：step URL **自带**查询串时以它为准，否则沿用 `base_url` 的 |
| 重定向控制（`allow_redirects`）、超时（`timeout`，三级可配）、证书校验开关（`verify`） | `step_request.py`、`utils.resolve_default_timeout` | ✅ ⚠️ **默认值是 `False`（即默认不校验证书）**，沿用上游取向；批次 C / M5 起每次运行会**提示一次**（每个进程），需要校验请写 `config.verify: true` 或请求级 `verify: true`。详见 §5.1 第 12 条 |
| **请求级代理 `proxies`、客户端证书 `cert`、流式读取 `stream`** | `models.TRequest`（0916-8 新增） | ✅ `tests/client_test.py::TestRequestProxies` 证明代理真的生效 |
| 响应侧：状态码、响应头、Cookie、body（JSON/文本/二进制）、耗时、响应体积 | `client.get_req_resp_record` | ✅ 0919-21 / H3：**记录体也支持裸 JSON 标量**。`RecordBody = Union[bool, int, float, Text, bytes, List, Dict, None]`，`RequestData`/`ResponseData` 共用。修复前联合类型里没有 `int/float/bool`，服务端返回 `123` / `true`（`Content-Type: application/json`）会在**记录这一步**抛 `ValidationError: 4 validation errors for ResponseData`——请求其实已经发出去了，整条用例的结果却被丢弃（`hrun` exit 1、报告无响应记录、extract/断言全不执行）。⚠️ 关联边界见 M14（**已修**：`json:` 现在也接受裸标量**请求**体，见上一张表的「JSON 请求体」行） |
| 记录 client/server IP:Port（chunked 响应也能统计体积） | `client.py` 的 `_get_connection_socket` | ✅ ⚠️ **边界（批次 C 复核实测）**：地址只能从底层 socket 读（requests/urllib3 无公开 API），而**服务端响应后关闭连接时**（HTTP/1.0、或响应带 `Connection: close`）urllib3 已把 socket 置空 → `AddressData` 静默退化为 `"N/A"/0`，只在 `.run.log` 里留一条 DEBUG（`raw socket is not accessible`）。HTTP/1.1 keep-alive 与重定向后的最终响应都正常（实测 `server_ip=127.0.0.1`）。`tests/client_test.py::TestHttpSession` 用的是本仓 httpbin mock（HTTP/1.1），所以覆盖不到这一形态 |

> 请求级字段完整列表（YAML 里的 `request:` 支持哪些键）：
> `method` `url` `params` `headers` `cookies` `data` `json` `timeout` `verify` `allow_redirects`
> `upload` `x_path` `proxies` `cert` `stream`。
> **写了不在这个列表里的字段会收到告警**（0916-8 起，见 `loader.warn_unknown_testcase_fields`）——
> 修复前这类字段会被 pydantic 静默丢弃（`extra="ignore"`），用户以为配了、其实没配。
>
> ⚠️ **`data` 与 `json` 不能同时写**（批次 B / M6 起是**响亮报错**）：requests 的语义是
> 「`data` 非空时**整个 `json` 分支不执行**」，也就是 `json` 会被**静默丢弃**——
> 实测 YAML 写 `data: "a=1&b=2"` + `json: {k: v}`，服务端只收到 `a=1&b=2`，
> 而 `hmake`/运行期都**零告警**（两个键都是正式字段，未知字段告警不响）。
> hint：URL 查询串请用 **`params:`**（`data:` 是**请求体**）。

### 3.3 提取与断言（A）

**提取**：`extract` + jmespath，可写 `body.data.token`、`body.items[0].name`、`body."user-agent"`（特殊字符加引号）；
提取路径里可以用变量/函数。→ ✅

**断言**：`validate` 支持新旧两种写法，短别名自动归一。**共 22 个内置算子**（18 个基础算子 + 4 个结构与契约算子）：

| 分类 | 算子（短别名 → 规范名） |
| --- | --- |
| 相等性（4） | `eq`→equal、`ne`→not_equal、`str_eq`→string_equals、`type_match`（无别名） |
| 数值比较（4） | `gt`→greater_than、`ge`→greater_or_equals、`lt`→less_than、`le`→less_or_equals |
| 长度比较（5） | `len_eq`→length_equal、`len_gt`→length_greater_than、`len_ge`→length_greater_or_equals、`len_lt`→length_less_than、`len_le`→length_less_or_equals |
| 集合/包含（2） | `contains`、`contained_by`（无别名） |
| 字符串形态（3） | `startswith`、`endswith`、`regex_match`（无别名） |
| **结构契约（1）** | `jsonschema_match`（**第 19 个**：响应符合 JSON Schema；`jsonschema` 是主依赖，schema 走文件路径或 `${func()}`） |
| **XML（3）** | `xpath_match` / `xpath_count`（**第 20/21 个**：完整 XPath 1.0）、`xml_schema_match`（**第 22 个**：XSD 契约校验）—— 后三个需要可选 extra `xml`（lxml），详见 **§3.10** |

> 依据：`builtin/comparators.py` 的**公开函数**（实测 **22** 个；生成期白名单 `make.BUILTIN_COMPARATOR_NAMES` 由它自动派生，条数一致）
> \+ `response.get_uniform_comparator`（12 个短别名映射）。
> 检查项（`check`）可以是 `status_code` / `headers.xxx` / `cookies.xxx` / `body.xxx`（jmespath）/ `text` /
> `elapsed_ms` / `elapsed_s` / `response_size` / `reason` 等。
> ⚠️ 数值算子两侧**都是字符串**时是**字典序**比较（`"9" > "100"` 为真）—— 批次 C / L11 起会告警，详见 §5.1 第 13 条。

**自定义断言算子（B，✅ 已验证）**：`response.validate` 用 `parser.get_mapping_function(assert_method)` 查断言函数，
查找顺序包含 `debugtalk.py`，且未知比较方式会原样保留——因此在 `debugtalk.py` 里写一个
`def has_keys(check_value, expect_value, message="")` 就能在 YAML 里直接 `validate: - has_keys: [body.json, [a, b]]`。
JSON Schema、XML 结构、业务语义校验都可以这样补，**不用改框架**（`tests/response_test.py::TestCustomComparator` 覆盖）。

### 3.6 环境与配置（A）

| --- | --- | --- |
| XML 结构化断言 `xpath_match` / `xpath_count` | **完整 XPath 1.0**：多级路径、`text()`、`count()`/`string()`/`boolean()`、位置谓词 `(//item)[2]`、属性取值 `@id`、轴 `ancestor::`；两种写法（**简化写法** `code` / `{URI}code` / `item[@id='1']` 与**原始 XPath**） | ✅ A2-1（需 `xml` extra / lxml）。简化写法按 `local-name()` 比对 → **命名空间前缀漂移（`ns1:`→`abc:`）也能断住**；批次 C / L13 修掉两处假失败（带前缀的选择器、根元素），详见 §5.1 与 `examples/soap_xpath/README.md` |
| XSD 契约校验 `xml_schema_match` | 「**契约即用例**」：`maxOccurs`/必填属性/取值 pattern 一次写进 XSD，用例里不必重复；支持**先定位业务元素再校验**（`{"xpath": "QueryResponse", "xsd": "schemas/query.xsd"}`，推荐——客户 XSD 通常只描述 Body 里那层元素）、`xs:include` 多文件、出错时给出**节点路径** | ✅ A2-2（需 `xml` extra）。`hmake` 阶段还会检查 **XSD 文件是否存在**、并拦下**内联 XSD 字符串**（报错里带已尝试的路径） |
| JSON Schema 契约断言 `jsonschema_match` | 响应体符合 JSON Schema（`$ref`/`required`/`type`/`format`/`additionalProperties` 都真强制）；schema 走**文件路径**或 `${func()}` | ✅ 主依赖（`jsonschema`）。⚠️ **内联 schema 仅当不含 `$` 键时可用**（`$schema`/`$ref` 会被框架当变量解析，`hmake` 阶段直接报错） |
| XML 响应里的**字符串片段**断言 | 用 `text` 前缀（`contains: ["text", "<ns1:code>0000</ns1:code>"]`）—— `text` 是 requests 解好的字符串；或 `type_match: ["body", bytes]` 断原始 bytes | ✅ |
| **零依赖退路**：项目级算子（A1） | 复制 `examples/soap/debugtalk.py` 的四段算子（`xpath_match` / `xpath_count` / `soap_fault` / `xml_field`）到项目 `debugtalk.py`，**不装 lxml 也能断 XML** | ✅ 现场装不了二进制 wheel 时用这个。⚠️ 它是简化子集的实现（简化写法 + Fault + 取值），**与内核算子命中集合一致**（护栏 `tests/xml_comparators_test.py::TestParityWithA1StdlibOperators`） |
| 跨步骤传递 XML 里取到的值 | 内核/项目级算子都不支持「extract 从 XML 取值」→ 在 `teardown_hooks`（**复数**！）里取值：本步骤用 `- code: "${xml_field($response, code)}"`，跨步骤写 `os.environ` 后用 `${ENV(...)}` 读 | ✅ 见 `examples/soap/chain.yml`（**规则：hook 赋的变量只在本步骤可见**） |
| ⚠️ 未做 | **WSDL 驱动生成用例** | ❌ 不做（属独立项目量级） |

> 用法与五个可离线复现的演示：[`examples/soap/README.md`](../examples/soap/README.md)（A1 零依赖）、
> [`examples/soap_xpath/README.md`](../examples/soap_xpath/README.md)（内核算子 + XSD）；

## 五、已知限制与「坑」

### 5.1 需要留意的行为（不是 bug，但要知道）

1. **HTTP 4xx/5xx 不会自动判失败**：框架只记录状态码，成败完全由你的 `validate` 决定——每个步骤都要写断言。
2. **`timeout` 默认 120s**（`INTERFACETESTER_TIMEOUT` 可整体覆盖），不会因为配置缺失而变成"无限等待"。
3. **`make` 生成的 `_test.py` 是产物**，改了下次 `hrun` 会被覆盖；要改就改 YAML。
4. **`debugtalk.py` 里函数参数不能直接写引号/花括号**：先用 `config.variables` 定义，再以 `$变量名` 传进去。
5. **测试用例文件不要放在仓库根直接 `hrun .`**：`load_folder_files` 会把 `_test.py` 一起收集（框架自身测试在 `tests/` 下，不建议在仓库根批量跑）。
6. **同一个映射里不能写重复的键（批次 A / H1 起会响亮报错）**：PyYAML 的语义是「后者胜、前者静默丢弃」，而键名都是**认识的字段**（`validate` / `setup_hooks` / `headers` / `request`…），所以未知字段告警、生成期闸门与 pydantic **三处都不会响**。实测后果：一个 step 里写两段 `validate:`，第一段里那条**故意失败**的断言整体蒸发 → `hmake` 退出码 0、零告警、`hrun` 报 1 passed（假通过）。现在 `loader` 在**加载层**判重并报错，报错里点出**键名 + 两处的行号**。
   - 合法写法不受影响：`<<:` 合并键 + 显式覆盖同名键（YAML 语义是"显式键胜出"）**不会**被误判；列表里的重复元素（两条一样的断言）也不是重复键。
7. **参数化数据集为空会报错（批次 A / H2 起）**：见 3.4 那一行。以前是静默 skip + `exit 0`。
8. **失败用例的耗时/体积等记录字段**（批次 A / M7 起）：`StepResult.content_size` 以前**全仓没有写入点**、恒为 0（与同一条记录里的 `data.stat.content_size` 矛盾），失败 step 的 `step_type` 还会泄漏枚举 repr（`request-MethodEnum.GET`）；现在都会写真实值（成功路径的 `step_type`（`"request"`）**逐字未变**）。
9. **源用例的文件名/目录名会成为 Python 标识符**（批次 B / M1）：`-`/`.`/空格 一律折成 `_`，**其它不能出现在标识符里的字符**（`+ @ & ' ( ) ! % , ; = [ ] ^ ` { } ~ $ #`）与**关键字**也一并折/挡掉，数字开头的段补 `T`。所以 `case+1.yml` → `case_1_test.py` / `class TestCaseCase1`。
   - 修复前只折那三个字符：`hmake` 会**退出码 0** 却产出 `class TestCaseCase+1(...)` 这种 `SyntaxError` 文件（直到 `hrun` 才报 `collected 0 items / 1 error`），而 `hconvert` 会因为**合法的 Postman folder 名**（`Auth + Token`）整体 `exit 1`（同一个根因的两个方向）。
   - 现在落盘前还有一道 `compile()` 兜底（`make.ensure_generated_python_is_valid`），把"生成成功但产物 import 不了"变成生成期可读报错。
10. **一个 step 只能是一种类型**（批次 B / M2 起）：`request` 与 `testcase`（含 v2/v3 的 `api`）**不能并存** —— 修复前那会让**整条引用用例被静默丢弃**（`testcase` 在 compat 重建 step 时被丢掉），被引用接口一次都不跑，父用例照绿。要串联就**拆成两个 step**。
11. **`--save-tests` 的落点**（批次 B / M3 + M4）：用例路径按「上一个 token 是不是会吃掉一个取值的 pytest 选项」判定（`-c pytest.ini case.yml` 里的 `pytest.ini` **不会**被当成用例）；`summary.json` 单文件是 `logs/<用例名>.summary.json`、目录与**多文件**是 `logs/all.summary.json`；conftest.py 写到用例所属**项目根**，找不到项目标记（没有 `debugtalk.py`）时改用**用例自己所在的目录**并告警 —— 修复前会写到兜底 RootDir（可能是 cwd 或祖先目录，实测写到过仓库根，并劫持同树下其它 pytest 会话的汇总输出）。
12. **HTTPS 默认不校验证书**（批次 C / M5 起**会提示一次**）：`verify` 的默认值是 `False`（沿用上游取向），而 `client.py` 在 import 期就关掉了 `InsecureRequestWarning` —— 于是「证书没校验」这件事**在日志里也看不到**。现在每**个进程**在第一次向 https 发请求且 verify 为假时打一条 WARNING，并给出 `verify: true` 的改法。**不影响任何行为**；测生产地址时请显式打开校验（`config.verify: true` 或请求级 `verify: true`）。
13. **数值算子两侧都是字符串 = 字典序比较**（批次 C / L11 起**告警**）：`greater_than: ["body.price", "100"]` 在接口把数字返回成字符串时会因 `"9" > "100"` 而**通过**（字典序），而反方向（一侧是数字）会抛错并给 hint —— 提示过去只覆盖失败方向。现在四个数值算子都会告警说明「这是字典序」并给出改法。**判定不变**（字典序对 ISO 日期串是合法用法，硬拦会假报）；比数值请把期望值写成数字。
14. **`$中文` 这类变量名写法不被支持**（批次 C / L12 起**告警**）：变量名必须以**字母或下划线**开头（`$中文` / `$1abc` 不匹配），它们会被**原样当字面量发出**；`${中文}` 至少还有一条「未被解析的 `${...}`」告警，`$中文` 以前**连告警都没有**。现在只要「这个名字确实在变量表里定义过」就会告警（纯字面量如 `价格 $100` 不误报），行为不变 —— 改法是把变量名改成 ASCII。
15. **SQL 账号/口令里的特殊字符可以放心写**（批次 D / T4 起）：连接串的 userinfo 由框架做 URL 编码，`p@ss word`、`a+b`、`p@ss/w%rd`、`中文密码` 都能原样送达驱动。修复前用的是 **`quote_plus`**（query string 的口径，空格 → `+`），而消费者 SQLAlchemy 用 `unquote` 解 userinfo（**不**把 `+` 还原成空格）→ 驱动拿到的是**被改过的口令**：现象是「认证失败/连不上，但 YAML 里写的口令明明是对的」，且除了「口令里有空格」没有任何线索。**库名不做编码**（SQLAlchemy 不解码 path 段，编了会把库名改坏）；`config.db` 与 `with_db_config()` 两侧同一口径。

### 5.2 已知缺口（按影响排序）

| 缺口 | 现状 | 影响 |
| --- | --- | --- |
| **`config` 级 hooks 不受支持（设计如此）** | HttpRunner v4 起只有 step 级 hook，`models.TConfig` 里没有这两个字段；`examples/httpbin/hooks.yml` 里那段 config 级 hook 是 v2/v3 写法、一直没有生效，**0916-8 已把示例订正到 step 级**并在 YAML 里写明替代做法 | 写了会被告警「无法识别字段」；用例级/会话级前置后置请用 `conftest.py` fixture |
| **`weight` 等 v2 遗留字段** | v4 无此概念，`examples/postman_echo/.../request_with_functions.yml` 里还留着一个 | 会被忽略（现在会告警） |
| **生成文件里 `client_secret` 明文** | `make.py` 只告警不阻断（建议写 `${ENV(...)}`） | 生成文件入库会泄密 |
| **脱敏的两个结构性盲区（L20，0919-22 登记）** | ① **转换层不检查字符串「值」内部**：`{"outer": "password=abc"}` 原样入库（`sanitize_body` 的既有口径是"只按**字段名**判定，不做值猜谜"——误伤业务字段比漏掉更麻烦）；② **完全无结构的裸凭据**判不出来：纯文本/XML 体里的 `the password is s3cr3t` 既非 JSON 也无 `k=v`，明文入库 | 属"按名判定"这一机制的天花板，**不是漏做**；两层松紧不同是有意的（转换层误伤会让生成的用例跑不起来，展示层误伤无害）。需要更强保证时请把凭据写成 `${ENV(...)}` 或结构化字段 |
| **SQL 只支持 MySQL、`config.db` 不可由 YAML 配置** | step 里硬编码 `mysql+pymysql://`；hmake 不渲染 config.db | 用别的库要改框架；YAML 写 config.db 无效（用步骤级 `with_db_config`） |
| **无并发治理 / 报告聚合** | `pytest-xdist` 能并行，但聚合、数据隔离、失败重跑要自己搞 | 用例规模大时明显 |
| **无测试数据管理约定** | 造数/清理全靠 `debugtalk.py` + SQL step | 用例间数据耦合风险 |
| **Thrift 未真实验证** | 见 3.9 | 别当成熟能力用 |
| **非 HTTP 协议** | gRPC / WebSocket / MQ / 私有 TCP 不支持 | 需要时得改框架或换工具 |
| **make 的模块级全局会跨调用累积** | `pytest_files_run_set` / `pytest_files_made_cache_mapping` 是进程级 set，程序化多次调用 `hrun`/`main_make` 时会互相带上对方的用例（写测试时需自行 clear） | 程序化集成时踩坑 |

> 「未知字段现在会告警」这件事本身是 0916-8 的改进：修复前 YAML 里写错字段名、
> 或者写 `proxies:`/`cert:` 这类当时不存在的字段，都会被 pydantic 静默丢弃，没有任何提示。

## 七、能力边界一句话版

> **对 HTTP/HTTPS 接口测试，这套框架功能闭环完整**（写→转→跑→提取→断言→报告→日志→CI），
> 配合 `debugtalk.py` 这个万能扩展点，能覆盖绝大多数企业接口测试需求；
> **SOAP/XML 接口的请求与结构化断言（XPath + XSD 契约，见 §3.10）也已内置**——
> 存量资产可用 `hconvert` 从 curl / HAR / Postman / OpenAPI 导入；
> **SQL 查询校验是内置可选扩展（仅 MySQL）；Thrift 是实验性且未验证**；
> **非 HTTP 协议、并发治理、测试数据管理、报告聚合属于框架之外**，需要单独投入。
