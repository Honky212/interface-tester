### R11-1　断言语义正确率阈值未定

- **现状**：§9.2 R11 的"可判定但语义错"是核心风险（过闸门 ≠ 语义正确）。验收要求"人工抽检断言语义正确率 ≥ 阈值"，但**阈值未定**。§12.8-⑪ 表 A 已备 13 条（=该轮全部落盘断言）但**未判**——因为该批产物 13 条全是 `equal(status_code)`、零字段级断言，协议级语义无歧义，"这条阈值在此批产物上测不出"。

### 9.8 响应字段口径决议（**B2**）与落地（2026-09-26）

> **决策**：真实文档里**没有「必填」列的字段表**，按结构**视为该接口的响应数据表**，

### 9.10 第二档 **WP2.2（证据绑定）** 落地（2026-09-26，用户指令"继续下一档，目标 80% 覆盖 + 通用性"）

#### 一、修了什么（四处，全部可判据）

| 处 | 问题（实测） | 修法 |
| --- | --- | --- |
| **① 容器名被当文档字段** | `check='body'` 时 ① 要求引用句里出现字符串 `body` → 理由印成"**断言字段 'body' 没有出现在引用句里**"，读起来像"模型编了个字段 `body`"（病因指错，人会去改一个没错的地方） | 新增 `_CONTAINER_CHECKS`：`body`/`data`/`headers`/`params`/`json`/`cookies` 指"**在哪一层找**"，① 对它们**不适用**；证据责任转由 ②（`expect` 字面量）承担 —— **判据没放松，只是搬到了该在的地方** |
| **② 引用写歪 → 直接降级** | ①引**标题**（`成功响应`）②引**自造锚点**（`response_example`，文档里 0 次）③只引了**字段说明单元格**（`操作是否成功`，而字段名 `success` 在**同一张表的另一列**）——三种坏法的共同点是"**引用选歪了，事实在文档里**" | 新增模块 **`citation`（引用解析与证据绑定）**：把引用解析成**文档里承载该事实的那一节**（标题 → 那一节；正文行 → 含它的那一节；找不到 → 含"事实 token"的最小节），再交给 T28 对账一遍；对上了**不降级**，但**逐条记账** |
| **③ 绑定窗口太宽 → ③ 误判** | 绑到**整节**（一张字段表含多行多类型）后，③ 限定词检查读到同表里**别的字段**的 `string` → 判 `qualifier-conflict`（"引用句说该字段是字符串，却断言 `int`"）**假红** | 窗口**窄化到承载该事实的那一行**（前提：该行含**全部**可用 token，所以 ② 不会因此失效） |
| **④ 扁平片少一行 → 本节的窗口被判成"别的接口"** | 模型通路的 `scope` 来自 `slicer` 的**扁平片**（21-45），而同一节的标题跨度是 **21-46**（片不含尾随空行）→ 用"整节被片包住"判片内**差一行** → 本节自己的窗口被判成"别的接口那一段"→ **拒绝绑定**（实测：`access_token` 明明在片内却被判 `quote-miss`） | 片内判据改为"**这一节的头行落在片内**" |

**配套（可见性，缺一不可）**：

- `Coverage.bound_assertions` + `Coverage.render()` 里的"其中 N 条**证据是工具绑定的**"；
- `unknowns` 里逐条 `quote-bound`（**交付物可见**），并按本仓口径**升级成 blocker `unknown-critical`**
  —— "证据是工具绑的、不是模型引的"这一点**必须被人看见并点头**，转正要
  `haify review --approve … --resolve-blocker unknown-critical`；
- **反方向也钉住**：绑了但随后被别的原因（如 ④ 示例值硬编码）拦下的断言**不留记录**（不许出现
  "产物里没有这条断言，报告却说它绑过"的悬空记录）。
- **模型通路的输入单位修订**（`model_input_slices`）：由"扁平片"改为"**接口段**（含子标题，

### 9.11 `type_match` 的类型名处置（2026-09-26，收掉 §9.10 三-1）

> （不是只摘那一条断言）。而真实客户文档的字段表写的就是 `number`，模型照抄就踩
> （§9.7 那轮 18 片里 **1 片的失败正是它**）。

**处置（`assembler.normalize_type_match()`）**——本仓口径"**能确定的确定下来，不能确定的响亮点名**"：

| 情形 | 处置 | 结果 |
| --- | --- | --- |
| 合法内置名（`int`/`str`/`dict`/`None`…） | 一个字都不改 | 断言留下 |
| **无歧义别名**（`string`/`字符串`→`str`、`整数`→`int`、`对象`→`dict`、`数组`→`list`、`double`→`float`…） | **归一**成内置名 | 断言留下、闸门满意 |
| **有歧义**（`number`/`数字`/`数值`：`int` 还是 `float`？） | **不许猜** → 摘掉该条断言并写 `unknowns`（`type-name-unusable`） | **用例照常产出**（其他断言不受影响） |
| 其它（模型编的用法，如 `eval`） | 同上，理由写明"既不是合法类型名也不在别名表里" | 用例照常产出 |

★两个设计点：

1. **合法名单的单一来源是闸门**（`gates._TYPE_NAMES`）——抄一份到装配器迟早与 S7 漂移，
   而漂移的表现是"装配器说合法、闸门说非法"这种**自相矛盾**的产物；
2. `type-name-unusable` **计入** `coverage.dropped_kinds` 的降级分类 —— 否则报告会说
   "降级 1 条"却不给原因（§9.9 那条"分母/分类要能对账"的口径）。

**判据（+4 条）**：`tests/assembler_test.py::TestTypeMatchExpectMustBeGateLegal`——
无歧义别名归一（8 个 subtest）/ **合法名一字不改**（成对判据）/ 有歧义 → 摘一条、
**另一条照常进用例** / **端到端：带 `type_match: number` 的草稿不再被 S7 拒**（闸门结论里无 `S7`）。

**诚实边界**：`number` **没有**被翻译成 `int`/`float`（那是猜，本仓不猜）→ 这类断言的
覆盖只能靠**人工填**或**文档作者把类型列写确定**；本轮只保证"它不再拖死整条用例"。

### 9.13 「生成 → 真跑一遍」打通（2026-09-26）与它量出的真实可运行率

> 用户指令：**"继续下一步，打通 `haify run`（生成 → 真跑一遍）"**。
> 产物：`probe_p2_prep/mock_file_service.py`（与文档同源的 mock 服务）+
> `probe_p2_prep/e2e_run_generated.py`（搬草稿 → 转正 → 真跑 → 汇总）→ `out_e2e_run.txt`；
> 产品侧修掉一个真缺口：**`haify gen --base-url`**（见下）。

#### 一、先修缺口：产物**没有 `base_url`，根本跑不起来**

| 项 | 内容 |
| --- | --- |
| 现象 | `haify gen` 产出的 `url` 是相对路径，而 `config` 里**没有 `base_url`** → `hrun` 第一句就报 `ParamsError: base url missed!`（实测） |
| 更正一处猜想 | `base_url: ${ENV(BASE_URL)}` **不管用**：内核 `parser.build_url()` 拿 `urlparse()` 判 `netloc`，变量引用没有 netloc → **同报"missed"**。所以 `base_url` 必须是**字面量 URL** |
| 修法 | ① `haify gen --base-url <url>`（两条通路都支持）→ 写进 `config.base_url`；② **不给就响亮提示**，并**把文档 §1.1 自己写着的服务地址摊出来**（`gen.documented_base_urls()`：开发/测试/生产三个）让人直接挑 |
| 判据（+4 条） | `tests/assertions_test.py`：给了地址 → 产物里真有 `base_url` 且不再警告 / ★**成对**：不给 → 提示里点名 `base url missed` 并把文档里的候选摊出来；`gen.documented_base_urls` 两条（真实文档捞出三个环境 + ★**成对**：`curl` 示例里的 URL **不许**混进候选） |

#### 二、mock 与链路（**同源但不是同一份东西**）

- `mock_file_service.py` **只照文档写**：路由 = `interface_sections()` 认出的 17 个 `METHOD /path`；
  响应体 = 该节 `**成功响应**` 的 json 块（逐字用文档的例子）；没有就退回统一响应格式信封；
  路径对但**方法不对 → 405**、路径不认识 → 404（**不假装成功**）。
- `e2e_run_generated.py` 走的是**用户会走的命令**：`haify review --approve`（要处置哪些 blocker
  由**产品自己的口径** `quality` 算）→ `haify run cases/<用例>.yml`（`jobs.run_job`：L3 闸门 → 子进程 → 留痕），
  失败的那几条再单独跑内核 `interfacetester.cli run` 抓**断言级差异**。

#### 三、实测（那次 `gemma4:latest` 复跑的 **17 份真产物**）

| 指标 | 值 |
| --- | --- |
| 转正（`review --approve`，逐条点名处置 `unknown-critical`） | **17 / 17** |
| 真跑（`haify run`） | **17 / 17 都跑起来了**（端点、方法、信封全部对上） |
| **真跑通过** | **2 / 17（12%）** —— 只有 `T1_2_认证方式`、`T2_3_查询目录` |
| 失败 15 条的分类 | ①`body` 上断言**请求字段**（`path`/`sourceDirName`/`targetDirName`）②期望值是**从文档 JSON 里剪下来的片段**（`success": true`）③断言值是**别的段**的（错误码 `FILE_1018` 断在成功路径上、`body.success == False`）④`schema` 断言与文档示例不符（`$.data` 期望 object、示例是 list） |

#### 四、★根因（**带文档原文**）：这份文档的「成功响应」**没有数据**

以 `2.1 创建目录` 为例，文档写的是：

```json
// **成功响应**
{"success": true, "errorCode": null, "message": "操作成功", "data": null}
```

**`data` 恒为 `null`** —— 而 `path` 只是**请求**字段（`| path | String | 是 | 新目录的完整路径 |`）。
于是"断言响应里的 `body.path`"**在这份文档的语义下不可满足**，任何照文档实现的服务都会判它失败。

★所以这次量出的 12% **不是工具坏了**，而是**两层的真问题**：

1. **文档缺陷**：成功响应不写数据 → 生成的用例只能测状态码/信封（**该走"文档缺陷回流"**，
   让作者补成功响应，本仓 `reports/doc_defects.md` 就是这条路）；
2. **断言语义闸缺位**：T28 只管"这个值**在文档里有没有出处**"，不管"这句话**讲不讲得通**"
   —— 于是 `expect='success": true'`（JSON 片段）、把**请求字段**断言在 **`body`（响应）** 上、
   把**错误码**断在成功路径上，**四条闸门一条都拦不住**（它们确实"有出处"✗）。
   ★**注意**：`type_match: [body.path, str]` 这类形态**确定性通路也在产**（它的输入就是**请求**字段表）
   → 这意味着这条缺陷**不是模型独有的**，而是"**请求侧字段 vs 响应侧字段**"这个归属维度**整体缺失**。

#### 五、下一档的核心项（本轮**未做**，避免在长会话末尾仓促改口径）

| 序 | 事项 | 为什么 |
| --- | --- | --- |
| **1** | **请求侧 / 响应侧字段归属**：`body.X` 的断言必须**对得上响应侧**（响应示例/响应表/`data` 结构），对上请求字段的要**响亮拒绝**或改写成"请求已发送"这类不依赖响应的断言 | 本轮 15 条失败里 **≥10 条**出自它，且**确定性通路同样中招**（口径改动，必须成体系做 + 成对判据） |
| 2 | **期望值语义闸**：`expect` 是 JSON 片段 / 结构标记（`":`、`{`）时拒绝（"这是从示例里剪下来的，不是契约值"） | 本轮 ①②类失败的另一种形态 |
| 3 | 成功响应为空（`data: null`）→ **文档缺陷回流**（`reports/doc_defects.md`，附"缺什么、怎么补"） | 让**文档作者**去修，而不是让用例去猜 |
| 4 | mock 侧：把"成功响应空"的端点也给出**契约级**响应（按 `响应字段表` 的类型合成值），用于**区分**"用例错"与"文档空" | 下一轮度量要用 |

③ 端到端**全部跑通**（17/17 起得来、端点/方法/信封全对、失败都能定位到具体断言）才是本轮"打通"的交付。

### 9.14 「响应侧归属」闸门（2026-09-26）——§9.13 量出的头号失败原因，已落地

> 承接 **§9.13 第五节第 1 项**：真跑 15 条失败里 ≥10 条出自"**在 `body` 上断言请求字段**"。
> 本轮把它做成**成体系的闸门**（产 + 拦两侧），并用**同一批真产物**量出效果。

#### 一、根因（一行代码）

`assertions.read_field_rows()` 只判"这张表有没有字段列"，**不判它是请求还是响应** →
文档 §2.1 的**请求**字段表里的 `path` 被判成响应字段，产出唯一断言：

```yaml
validate:
  - type_match: [body.path, str]      # ← 而文档的「成功响应」写着 {"success": true, …, "data": null}
```

**照文档实现的服务必然让这条断言失败** —— 这不是"用例不够好"，是"**断言对象取错了**"。

#### 二、判据（**只看文档，不猜**）

`body.X` 合法 ⟺ 文档在**本接口段**里把 `X` 写在**响应侧**。响应侧证据三条来源：
①**无「必填」列**的字段表（口径 B2：那是响应数据表）；②**响应说明句**（``- `data.x`：整数``）；
③ **成功响应示例**的 JSON 键（含嵌套）。

四条**边界**（每条都是实测踩出来的，见第五节）：

| 口径 | 内容 |
| --- | --- |
| **粒度是"节"** | 不是整篇。按整篇并集时 `body.path` 会被**别的接口**的响应示例（元数据里也有 `path`）救活 ✗ |
| **只认最内层匹配节** | 祖先节（一级标题的整篇跨度）的名字是**子树并集** → 拿它判 = 拿整篇判 ✗ |
| **歧义引用句取并集** | 引用句可能指多节（`请求体`/`成功响应` 这种标题多处都有）→ 只在"**每一节都没有**"时才敢判不在响应侧（原先"挑最短那一节"把 `body.amount` **误摘**了 ✗）|
| **公共节要收窄** | 只认"**统一响应/返回/格式/规范/说明**"这类，且**跳过文档标题那一节** —— 实测 `# 统一文件服务平台-接入应用接口文档` 的"统一"把根节（全篇）判成公共节 ✗ |
| **容器名豁免** | 沿用既有 `_CONTAINER_CHECKS`（`body.data` 说的是"有个 data 容器"，不是"文档声明了 data 字段"）——不豁免会把 S1 该硬拦的**空 schema 陷阱**先摘掉，变成"零断言但合法" ✗ |

**判不了就不判**：引用句在文档里定位不到 → 放行（"拿不准就摘"会让闸门变成噪声源，T10 守的是这个）。

#### 三、两侧改动（**产 + 拦**，同一份口径）

| 侧 | 改动 | 关键点 |
| --- | --- | --- |
| **产**（确定性通路） | `derive_from_field(row, response_names=…)`：请求侧独有 → **一条断言都不产**，只回原因（`NOTE_RESPONSE_OWNERSHIP`）；`read_field_rows` 的**参数表**（根不是内核认的检查项）同理 | 报告里"没断言什么"**要能看见** |
| **产**（正面半） | 新增 `derive_from_response_examples()`：**成功响应示例**里的**标量** → `equal`（bool/null/数字）/ `type_match str`（字符串：示例值会变，只断类型）；容器不按值断言；**失败响应不产**（要靠非法请求触发，断言进正常用例正是实测里的一大类失败） | 没有它，归属闸门会让"只写信封"的文档**一条断言都不剩** |
| **拦**（模型通路） | `assembler.check_response_ownership()`：`body.X` 的 `X` 不在响应侧 → 摘掉（`kind=response-ownership`，DEGRADE 档，计入 T28 降级统计） | ★**顺序放在 T28 之后**：REJECT 级判据必须先出结论（实测：陷阱夹具的空 schema 若先被本闸门摘掉，S1 就再也看不到它 ✗） |

#### 四、实测（**同一批真产物，只换口径**）

| 度量 | 结果 |
| --- | --- |
| 确定性通路（真实文档 17 段） | 每段有可跑的断言（信封 + 响应侧字段）；`response-ownership` 降级**可见**；`_oauth2_token` 段 0 断言 → **响亮拒绝** ✓ |
| 模型通路（**离线重装配** 17 份快照，`probe_p2_prep/reassemble_offline.py`） | 装配 17/17 成功；`response-ownership` 降级 **3 → 12 条**（收紧"公共节/最内层"两处之后才真的生效） |
| **端到端真跑**（`probe_p2_prep/e2e_run_generated.py`） | **2/17 → 4/17（12% → 24%）**；剩余 13 条失败**全是另一类**（见第五节） |

★度量手段本身也是本轮产出：`.ai/draft/<用例>.draft.json` 存着**模型原始草案**，拿它过 `assemble()`
就是"**同一份输入、不同口径**"的对照（重跑模型既花钱又换随机性 ✗，不可比）。

#### 五、本轮踩到的坑（**全部由探针/实测救场**，不是设计出来的）

1. **文档级并集**：`body.path` 被别的节的响应示例救活 → 必须按**节**判；
2. **祖先节并集**：根节跨度是全篇 → 闸门形同虚设（`response-ownership` 只有 3 条）→ 只认**最内层**；
3. **歧义引用句**：`请求体` 在多节都有 → "挑最短那节"把 `body.amount` **误摘** → 改**并集**；
4. **文档标题**里的"统一"命中公共节正则 → 根节又变公共节 ✗ → 正则收窄 + 跳过 `start_line==1`；
5. **容器名**未豁免 → 空 schema 陷阱被"先摘掉" → 变成"零断言但合法"，被 `TestGateAndBudget` 当场抓住；
6. **L3 沙盒**：`haify run` 被拒（`l3_refused`，"沙盒未开启"）—— 这是本仓**有意**的保险；
   端到端脚本必须显式 `INTERFACETESTER_AI_SANDBOX=on`，且**把拒因打出来**（否则只看到退出码 2 会误判成"用例跑挂了"）。

#### 六、登记的新项（本轮**未做**）

| 序 | 事项 | 证据 |

### 9.16 「文档写明的请求参数真的发出去」（2026-09-27）——§9.14 第六节第 2 项，已落地

> 承接 **§9.14 第六节第 2 项** / **§9.15 第四节第 3 项**：`to_draft_payload` 只写 `method`/`url`，
> **文档写明的请求参数一个都没发出去**。用例"能生成、能加载、能断言"，但对真实服务是**空请求**。

#### 一、为什么不能"直接把字段表塞进 json"（先量后改）

在真实客户文档上量的（探针可复算）：

| 量到的 | 数值 |
| --- | --- |
| 字段表行 / 必填字段 | 147 / **64** |
| 必填字段的**落点分布** | **全部 `body`** —— 连 `Authorization`、`X-Path`、`Content-Type` 也是 |
| 原因 | 请求头表首列写的是「**头名称**」→ 命中 `_FIELD_COL_RE` 的"名称" → 被当**请求体字段** |
| 能从「请求体示例」拿到值的 | **5 / 64** |

⇒ 若直接按行生成 `json`，会产出 `json: {Authorization: …, X-Path: …, Content-Type: …}` ——
**比"不发参数"更坏**（结构错、服务端必然拒绝）。所以必须**分层**做。

#### 二、三层解法（本轮做完前两层）

**第 1 层：落点识别（顺序即口径）**

| 判据 | 落点 |
| --- | --- |
| 表首列「头 / 头名称 / header」 | `headers`（★**必须先判头**，否则「头名称」会被"名称"捞走） |
| 表首列「参数 / query / param」 | `params` |
| 其余（字段 / 名称 / name / key …） | `json`（`x-www-form-urlencoded` → `data`） |
| 本节写 `multipart/form-data` | **不落**（`upload` 不在产物契约里）→ 点名交人工 |
| **GET / HEAD 段**（协议事实：没有请求体） | 该段的"请求体表"按 `params` 发；**断言侧同样不产 `body.*`** |
| 判不了 | **不落**（宁缺勿错） |

**第 2 层：取值来源（每一档都有出处，不编）**

    ① 表格「示例值」列  →  ② 本段「请求体示例」的同名字段  →  ③ `${ENV(TODO_<字段>)}` 占位

无条件特殊处理：**凭据名**（`Authorization`/`token`/`password`/…）→ `${ENV(名字)}`（**不抄文档里的 token**）；
**可选字段 → 默认不发**（与"可选字段不断言"同一精神）；**JSON 体自动补 `Content-Type`**（协议事实，记进 notes）。
★N 条说明全部进 `unknowns`（可选几个没发 / 哪些成了 `TODO_` / 凭据怎么处理 / 内容类型怎么定的）——
**可见，不静默**。★`todo_findings` 同时补扫**请求值**（否则"参数还没填"只在 `promote_draft` 的拒绝里看得见 ✗）。

**第 3 层：可跑性（本轮不在范围）**：值拿不到 → `TODO_` → 运行期 `EnvNotFound` **响亮报错**（这是要的语义）。
要真跑绿还得有**测试数据来源（造数）**——独立议题（`docs/能力清单.md` §5.2 已登记"无测试数据管理约定"）。

#### 三、纪律边界（写进代码注释，避免下一个人误判）

1. **示例值当"请求值"合法，当"期望值"不合法** —— T28 ④ 管的是 `expect`；两者不冲突；
2. **拿不到值不猜**：`${ENV(TODO_…)}` + 登记 pending + 只落 `.ai/draft/`；
3. **凭据不进产物**（连文档示例里的真 token 也不抄）；
4. **公共节只继承请求头**（"公共请求头"是唯一常见形态；把公共的请求体/响应表也套给每个接口就是"错位"）。

#### 四、实测（同一份真文档 + 与文档同源的 mock）

### 9.18 curl 示例当取值来源（2026-09-27）——§9.16 第六节第 1 项，已落地

> 「复制为 cURL」是接口文档里最普遍的一档"**能跑的请求**"：真实客户文档有 **16 处 curl**，
> 每处都带 `-H`（含 `X-Path`/`Authorization`）、`-d` 与 URL 查询串。

**取值优先级（`request_payload_from_rows`）**：

    ① **本段 curl 示例** → ② 表格「示例值」列 → ③ 本段「请求体示例」同名字段 → ④ `${ENV(TODO_…)}`

★为什么 curl 排第一：它是一次**完整、可跑的调用**（头 + 体 + 查询串都在），比"只给一格的示例值列"更接近真实请求。
★两条纪律**不变**：curl 只作**取值来源**（**表里没有的名字不凭空加**）；凭据仍走脱敏
（`-H "Authorization: Bearer REAL-TOKEN"` → 产物里只有 `${ENV(AUTHORIZATION)}`）。
★口径：`-d/--data*` 的值**能解析成 JSON 对象**才算 `json`（不是 JSON 的不猜）；URL 的 `?a=1&b=2` → `params`（值 URL 解码）。
★实测踩到并修掉：`-d '{"a": 1}'` 里**外层单引号内还有双引号** —— 原来的 `[^"']*` 把双引号排除，导致
**永远匹配不到**；现在用 `"([^"]*)"|'([^']*)'` 两种引号各一支（`_curl_quote_value` 取非空那支）。
另一个真缺陷：curl 的键是"**桶**"（`json`/`params`/`headers`）、行上是"**location**"（`body`/…）——
`body ↔ json` 对不上，于是 curl 的值**永远取不到** ✗ → 现在先算"目标落点（桶）"再谈取值（顺序即口径）。

**判据（`TestRequestPayloadFromFieldTables` 内 4 条）**：curl 值优先于示例值列 + 真 token 不落产物 /
URL 查询串 → `params` 且**表里没有的键不凭空加** / ★成对：curl-only 的头与字段**不许**进请求 /
★成对：没有 curl → 仍按示例值列（老行为）。

### 9.21 「负例步骤能不能真跑」——文档驱动的**错误条件引擎** + 正例/负例分开统计（2026-09-27）

> 承接 **§9.15 第四节登记的第 1 项**："mock 按文档的错误条件触发失败 …… 这是当前'真跑'
> 能不能继续往上走的**唯一瓶颈**"。

#### 一、瓶颈长什么样（先量）

模型产出的**负例步骤**是这样的（真产物）：

```yaml
- name: 路径不匹配时返回错误码            # ← 第 2 步
  request: {method: GET, url: /api/metadata/query,
            headers: {X-Path: /app1/correct/}, params: {path: /app1/wrong/}}
  validate: [{contains: [body, FILE_1018]}]
```

而 mock 只会照文档的**成功响应**应答 → 这一步**永远红** ✗ —— 但红的根因**不是用例错**，
是"服务端没模拟错误条件" ✗。**归因不清 = 指标不可信**。

#### 二、做法：从文档里**推导**可判定的错误条件（不是硬编码错误码）

`probe_p2_prep/mock_file_service.py` 新增**规则引擎**：

| 步 | 做什么 | 实测（真实文档） |
| --- | --- | --- |
| ① 候选句 | 全篇含错误码的句子（**含公共错误码表**那种行，如 `\| FILE_8002 \| 开始时间不能大于结束时间 \|`） | 35 条 |
| ② 关系词 → 谓词 | `完全一致/相同`→`==`、`不一致`→`!=`、`不能大于/不超过`→`<=`、`大于/小于`→`>`/`<` | — |
| ③ 绑两个字段 | 先取**反引号里的名字**（`` `X-Path` ``/`` `path` ``）；没有名字时按**字段说明的用词**（「开始时间」→ `startTime`） | **绑定 10 条**（8 个接口） |
| ④ **取反** | ★文档写「**必须**与…一致」是**要求**，mock 要的是**违反条件**（不一致才报错）→ 取反；而「`startTime` **大于** `endTime` 时返回 X」本身就是违反条件 → 不取反 | 不取反会"正例全红、负例全绿"（方向反了）|
| ⑤ 判不了就**点名** | 要状态/文件大小/业务状态的（如「文件超过 50MB」）→ 进"**不模拟**清单"，启动打印 + 报告列出 | **不模拟 25 条**（逐条点名）|

命中时按该节**失败响应示例的形状**回失败体，`errorCode` 换成命中规则的码（**码同时进 `message`**，
免得断言写法影响结论）；并把"命中了哪条规则"一起写进**回读文件** ✓。

#### 三、★连带更正一条 §9.15 的判据（`contains` 对字典的行为）

实测：mock 已经回 `{"success": false, "errorCode": "FILE_1018", ...}`，而 `contains: [body, 'FILE_1018']`

    ③-b `contains`/`not_contains` + 容器 + `expect` **不是文档化的键名** + 本节响应是 **JSON 对象**

★成对：本节**没有** JSON 对象示例 → 判不了 → 放行。

## §9.25 给 `fix` 扩触发面（2026-09-27 落地，**已实测**）

### 1. 先纠正"扩面"的含义

§5.8 原文把触发条件**钉死在两族**：「`check_value is None` + jmespath 路径类断言」与
「`type_match`/字段名类失败」，并明写 `status_code`/业务码类一律判疑似真实缺陷、不给改。
所以本轮做的是**把这两族的覆盖补全**（不是自创新族），并**每扩一分配一道更硬的闸**。

### 2. 补全时发现三个真缺陷（都属"改了语义而不是改名字"）

| # | 缺陷 | 后果 |
| --- | --- | --- |
| a | **容器被吃掉**：改前无论 `check` 的根是什么，候选都只在**响应体**里找、并一律拼成 `body.*` | `headers.X-Foo` 取不到值会被"修"成 `body.XFoo` ✗（**换语义**） |
| b | **`${var}` 被当成路径**：`${token}` 走的是"路径失效"分支 | 会被改成 `body.token` ✗✗（把变量引用换成响应字段） |
| c | **引号被吃掉**：`yaml.compose` 的 mark **含引号**，替换时直接吃掉了它 | `["${x}", "abc"]` → `[${new}, "abc"]` —— 流式序列里 `{`/`[` 是**语法字符** → 补丁解析不过 → 双前置拦下 → **"该给的建议一条也给不出来"** ✗（同样影响 `body.items[0].id`） |

## §9.29 响应 Cookie 成为可查事实（2026-09-27 落地，**已实测**）

> 来源：§9.28 第 5 节**登记项 2**（= §9.25 第 7 节的同一项）：「`cookies` 仍未支持
> （**需先让"响应 cookies"成为可查事实**）」。现已落地。

### 1. 缺口在哪

内核**一直**支持 `cookies.*`（`interfacetester/response.py`：`resp_obj.cookies.get_dict()`
→ **字符串字典**）；`KERNEL_CHECK_ROOTS` 里也一直有 `cookies` ✓。缺的是**中间那一环**：
**文档里怎么声明"这个接口会下发哪些 cookie"** —— 文档写了也没人认，于是 cookie 断言只能手工写，
或者干脆没有 ✗（与 §9.27 的"头表读不到"、§9.26 的"大小事实"同一种形态：**事实没进链路**）。

### 2. ★一轮自查纠正（这一条值得记）

第一版实现是「**一条 `jsonschema_match` 断言 cookie 类型是 `string`**」。写完立刻发现它**错的**：

> cookie 值在内核里**恒为字符串**（HTTP 协议如此）→ `type: string` 这条断言**永远为真、零信息量** ✗，
> 正是本仓最反对的"看起来在断言、其实什么都没判"（假通过）。

改成「**只在文档给出可判据事实时才产断言**」：

| 文档里写了什么 | 产什么断言 |
| --- | --- |
| 说明列标「**固定值**」+ 值列给了值 | `equal: [cookies.<名>, <值>]` ✓（**有牙**） |
| 说明列给了「**取值：A / B**」 | `contained_by: [cookies.<名>, ['A','B']]` ✓（按**字符串**比，防必红） |
| **两样都没有** | **不产断言**，但**认下这个事实**并**逐条点名** ✓（不硬凑） |

### 3. 落地（三处，其中两处是"单一来源"）

1. `doc_quality.COOKIE_COL_RE`：列头词表的**唯一来源**（与 `HEADER_COL_RE`（请求头表）/
   `PARAM_COL_RE`（查询参数表）同级——都决定"这张表说的是**哪一部分**"）；
2. `assertions.cookie_declarations()`：**断言与 mock 共用的唯一解析**。
   判据 = 首列是 `Cookie` / `Set-Cookie`（含「Cookie 名」）**且没有「必填」列** ——
   带必填列的是**请求**侧（列"要发出去的 Cookie"），那走请求头表 + 凭据脱敏 ✓；
3. `assertions.cookie_mock_values()`：**mock 该下发哪个值**（固定值 → 用它；枚举 → 第一个；否则 `mock-<名>`）
   —— 与**断言的期望同一份判据**。★这一条是"防假失败"的关键：mock 若自己造 `mock-variant`

## §9.30 「必带」建模 → 安全的 presence 断言（2026-09-27 落地，**已实测**）

> 来源：§9.29 第 7 节**登记项 1**：「『必带』断不出来 —— 本轮只断言"值是什么 / 落在哪个集合"」。

### 1. 缺口

§9.29 之后 cookie 能断"值是什么"（固定值 → `equal`）与"落在哪个集合"（枚举 → `contained_by`），
但**断不了"这个 cookie 一定会下发"** ✗。原因是刻意定的口径：响应侧默认**不写 `required`**
（文档没建模"什么时候会 set"，写了就是**误报** ✗ —— 这正是 §9.19 之前"必填列没写清"那类坑的同族）。

**要断"必带"，只能让文档先建模。** 这就是本轮做的事。

### 2. 文档怎么写（两种，都必须是**文档明写**）

```markdown
#### 响应 Cookie

| Cookie | 值 | 必带 | 说明 |
| --- | --- | --- | --- |
| sessionId | sess-1 | 是 | **固定值**：登录成功后总是它 |
| variant | - | 否 | 取值：A / B |
| theme | - | 否 | 主题偏好（可选返回） |
```

或（不新立列）在说明列里写「**必带** / 总是下发」这类标记词。

★**词必须换**：**不能用「必填」** —— `REQUIRED_COL_RE` 里的「必填」是**请求侧**判据，
带它的表会被当成**请求表**（落点进 `request`、不产响应断言）→ 方向就反了 ✗。
新增 `COOKIE_ALWAYS_SENT_COL_RE`（`必带 / 必下发 / 总是下发 / 总会下发 / always`），
**列头词表的唯一来源仍在 `doc_quality`**（与 §9.19 / §9.29 同一条纪律）。

### 3. 产什么断言

`jsonschema_match: [cookies, {"type": "object", "required": ["sessionId"]}]` ✓

★**为什么这里写 `required` 是合法的**（与响应数据表"不写 required"并不矛盾）：

| | 文档有没有建模"一定会给" | 该怎么断 |
| --- | --- | --- |
| 响应数据表（默认） | **没有** | **不写** `required`（写了就是替文档假定 → 误报 ✗） |
| Cookie 表标了「必带」 | **有**（文档明写） | **写** `required`（服务端不给 = **文档被违反**，真缺陷 ✓） |

判据差别就在这一点 —— 同一句话（`required`）在不同的**文档证据强度**下，一个合法、一个误报。

### 4. 实测：★**牙齿对照**（本轮新增的验证形态）

同一份用例跑**两台 mock**（唯一变量是"文档里有没有声明这些 cookie"）：

| mock | 行为 | 结果 |
| --- | --- | --- |
| 按文档声明下发 | `Set-Cookie: sessionId=sess-1; variant=A; theme=mock-theme` | **`1 passed`** ✓ |
| **不声明、不下发** | 响应里一个 cookie 都没有 | **`1 failed`** ✗（`equal` / `contained_by` / **`required`** **三条全红**）✓ |

★**这一对照是"判据有没有牙"的机器证明**：若两遍都绿，就说明断言**永远为真、零信息量** ✗
（正是 §9.29 自查纠正要防的形态）。以后凡"新增一类断言"，都该配一个这样的对照。

### 5. 判据（`tests/assertions_test.py::TestResponseCookieTables`，**+6**）

「必带」列 → `required`（且**不mix 非必带的**）✓ / 说明标记词同样认 ✓ /
必带 + 固定值 → **两条**断言各查各的 ✓ / 不标 → **无** `required`（成对：不误报）✓ /
有「必带」列但一行都没写清 → **点名**（不替文档假定）✓ / **元护栏**：加一行必带 → 列表跟着变 ✓。

### 6. 仍未做（登记）

1. ~~「必带」目前**只在响应 Cookie 表**上生效；**响应数据表**要不要也支持同样的建模
   （`required` 语义相同，但会影响面更大，需单独评估）~~
   → **已落地（2026-09-27）**：见 **§9.31**（必备词表通用化 + `_put_nested_required` 挂对层级 + 矛盾输入不硬判 + 牙齿对照）；

## §9.31 「必带」推广到响应数据表（2026-09-27 落地，**已实测**）

> 来源：§9.30 第 6 节**登记项 1**：「『必带』目前只在响应 Cookie 表生效；响应数据表要不要也支持」。

### 1. 缺口与**风险点**

§9.30 之后，响应 Cookie 表能标「必带」→ `required` ✓；而**响应数据表**（`body`）仍刻意
**不写 `required`**（口径 B2：文档没建模"什么时候会返回"）。要断"这个字段服务端一定会给"，
同样**只能让文档先建模** —— 本轮把**同一套判据**推广过去。

★推广的**风险点不是"要不要写 required"，而是"写在**哪一层**"**：

```text
文档：| fileName | string | 必带 | 文件名 |        ← 裸字段名 → 挂在 `data` 下
正确：{"properties": {"data": {"properties": {...}, "required": ["fileName"]}}}   ✓
错误：{"properties": {...}, "required": ["fileName"]}                              ✗
      （语义变成"顶层必须有 fileName" —— 响应里它其实在 data 下 → **必红**）
```

### 2. 落地（四处）

1. 新增 `_put_nested_required(schema, container_path, leaf)` —— **逐层建**，
   与 `_put_nested` 同源（容器骨架是同一套，两处各写一份迟早漂移）；
2. 「必带」词表**通用化**：`COOKIE_ALWAYS_SENT_COL_RE` → **`ALWAYS_SENT_COL_RE`**
   （判据本身与容器无关；名字里的 `COOKIE_` 会让人以为只管 cookie）；
3. ★**矛盾输入不硬判**：同一行既标「必带」又写「仅当…时返回」→ **不写** `required` + **点名**
   （替文档拍板会造出必红断言 ✗ —— 与 §9.14 的"条件返回不做存在性断言"同一条精神）；
4. ★**必带与类型无关**：类型判不了（如 `number`）也要断"有没有" —— 所以必带那段代码放在
   **类型检查之前**（否则一个类型写不清的必带字段会被静默漏掉 ✗）。

### 3. 与老行为的关系（**成对**，一起看才完整）

| 文档 | 产什么 | 判据 |

| 同一张表里标了「必带」 | **写** `required`（挂在正确层级） | `TestResponseTableAlwaysSentFields` ✓ |

## §9.33 响应头成为可判据事实（2026-09-27 落地，**已实测**）

### 1. 现场（登记项转正）

§9.32「仍未做」第 3 条：*「`cookies` 之外的**响应头**仍只有 `headers.*` 可手工断言」* ——
文档里明明写了响应头，工具却读不出来。它与 §9.29/§9.30/§9.31 是**同一条线**：
**先让文档能声明事实**，工具才有得判（同 §9.26「先让'大小'这个事实进请求」）。

### 2. 表形态判据（**两条一起**，缺一不可）

| 判据 | 为什么 | 反例（会怎么坏） |
| --- | --- | --- |
| 首列命中「头」/`header`（`HEADER_COL_RE`） | 复用既有词表（单一来源） | 无此判据则任何表都可能被当响应头表 |
| **没有「必填」列** | 带「必填」的是**请求头**表（要发出去、走凭据脱敏 `\${ENV(...)}`） | 方向反了：把请求头当响应头 → 产出必红的 `headers.X` |
| 表**前 15 行**窗口里出现过"响应/返回"字样 | 与 `_note_field_paths`（§9.20）**同一道闸** | "请求头表**恰好忘写必填列**"会被误当响应头表 |

★为什么**不**拿"小节标题叫『响应头』"当判据：标题写法没有约束力（客户文档里
`### 响应头` / `#### 响应` / 正文一句"响应头如下"都出现过）。窗口判据是**容错**的那一侧，
而"必填列"是**判向**的那一侧——两者合起来才够稳。

### 3. 值语义：只认「固定值」与「枚举」；其余**点名**

| 文档怎么写 | 产什么 |
| --- | --- |
| 说明列标「固定值 / 固定为 / 恒为」**且**值列给了值 | `equal: [headers.<名>, <值>]` |
| 说明列写「取值：A / B」 | `contained_by: [headers.<名>, ['A','B']]` |
| 两样都没写 | **不产断言** → **逐条点名**（"响应头值多半易变，要断请让文档补固定值或取值"） |

★**没有**类型断言：响应头类型**恒为字符串**（协议如此）→"断言它是字符串"**永远为真、
零信息量** ✗ —— 这与 §9.29 把 `type_match` 从 cookie 断言上摘掉是**同一个自查**。

### 4. mock 侧：**按同一份判据**下发（值同源）

`response_header_values(doc)` 与断言的期望出自**同一个** `response_header_declarations()`
（§9.29 的教训：mock 自造值 → **假失败**）。两条边界：`Content-Length` 由 mock 按真实字节算、
**不许**被文档覆盖 ✗；文档声明了 `Content-Type` 就**不下发**默认那个 ✓。

### 5. 实测（`probe_p2_prep/probe_response_header_fact.py` → `out_response_header_fact.txt`）

夹具文档 = 一张响应头表（固定值 / 枚举 / 无据各一行）+ 请求体表 + 成功响应示例：

- ① 确定性通路退出码 `0`，`1/1 条接口段产出草稿`；
- ② 草稿里：`equal: [headers.X-Api-Version, v1]`、`contained_by: [headers.Cache-Control, no-store、max-age=60]`；
- ③ 转正 + 真跑（mock 按文档下发 3 个头）：**`hrun` 退出码 0 → `1 passed`**；
- ④ run.log 原文：`assert headers."X-Api-Version" equal v1 ==> pass`、
  `assert headers."Cache-Control" contained_by ['no-store', 'max-age=60'] ==> pass`；
- ⑤ ★**牙齿对照**：同一份用例 + 一台**不下发这些头**的 mock（文档里删掉那张表）
  → **`1 failed`**（`check_value: None`）—— 判据**有牙**，不是"永远为真"。

▲★**本轮踩到并修掉的一个真缺陷**（值得记）：推导侧原本把**孤立的表块原文**再喂回
`response_header_declarations()` → 那个函数会**重跑**"附近有没有『响应』字样"这道窗口判据
→ 窗口为空 → **一行都取不到**（实测症状：断言**全空**、判据 4 条全红）。
修法：抽出 `_header_rows(header, body)`（**只取行、不判向**）供文档级扫描与推导侧共用
——"判向"只做一次、在文档上下文里做。

### 6. 判据（`tests/assertions_test.py::TestResponseHeaderTables`，**+7**）

固定值 → `equal` ✓ / 枚举 → `contained_by` ✓ / ★**无据 → 不产 + 点名**（成对）✓ /
★**带「必填」的请求头表 → 不产**（成对）✓ / ★**窗口里没有"响应"字样 → 不产**（成对）✓ /
★断言**必须带真实行号**（`line_no > 0`——段外过滤靠它，§9.29 的 cookie 断言曾因缺行号被整条丢弃）✓ /
★**元护栏**：改文档里的枚举取值 → 断言跟着变（不是写死的）✓。

### 7. 仍未做（登记）

   按"没声明就摘"会**误摘**）；

3. ★**推导层的降级说明进不了 `unknowns`**（本轮实测暴露，**影响面是整篇文档、不止响应头**）：

   `skipped` 的**契约加行号**（现在只有文案），才能**逐段归属**；属独立一件事；
4. 更早三项不变：mock 选"响应示例"的启发式陷阱、模型通路 `gemma` 系 `<unused50>` RCA、
