# InterfaceTester（Python 版）使用教程

> 项目路径：本仓库根目录（下文的相对路径都以它为基准）
> 版本：5.0.1（纯 Python，pytest 驱动，命令行工具，**不是 Web 页面**）

本教程按「写用例 → 命令行运行（含 `hconvert` 资产导入）→ 理解转换/发请求/断言 → 看 HTML 报告」四步带你上手，
文末的「进阶（续）」覆盖 **契约断言（`jsonschema_match`）、测试数据管理、CI 落地**。

---

## 0. 前置准备：激活虚拟环境

每次打开终端先激活 venv（否则 `hrun`/`hmake` 找不到，还会因 `black` 不在 PATH 报错）：

```powershell
# 在仓库根目录下（Windows）
.\.venv\Scripts\Activate.ps1

# macOS / Linux
source .venv/bin/activate

# 验证
hrun -V        # 应输出与 interfacetester/__init__.py 里的 __version__ 相同的版本号
```

## 第一步：编写接口用例

### 1.1 用例长什么样：两种写法

InterfaceTester 支持两种用例形式，**本质等价**（YAML 会被自动转成 Python）：

| 形式 | 文件后缀 | 适合人群 |
|---|---|---|
| **YAML/JSON** | `.yml` / `.json` | 入门、无代码、清晰 |
| **pytest 风格 Python** | `_test.py` | 会 Python、需要复杂逻辑 |

下面以 **YAML** 为主讲解（推荐先学这个）。

### 1.2 YAML 用例的完整结构

一个用例 = 一个 `config`（全局配置）+ 一串 `teststeps`（测试步骤）。每个步骤是一个 HTTP 请求，可带「提取」和「断言」。

```yaml
config:
    name: 登录并查询用户信息          # 用例名（必填）
    base_url: http://your-server.com   # 可选：基础地址，步骤里的 url 可写相对路径
    verify: false                      # 可选：是否校验 HTTPS 证书
    variables:                         # 可选：全局变量
        env: prod

teststeps:
  - name: 登录获取 token               # 步骤名（必填）
    request:
        url: /api/login                # 相对路径，会拼上 base_url
        method: POST                   # GET/POST/PUT/DELETE/PATCH/HEAD/OPTIONS
        headers:
            Content-Type: application/json
        json:                          # JSON 请求体
            username: admin
            password: "123456"
    extract:                           # 可选：从响应里提取变量，供后续步骤用
        - token: body.data.token       # 把响应里的 token 存成变量 $token
    validate:                          # 断言（校验响应是否符合预期）
        - eq: ["status_code", 200]     # 状态码等于 200
        - eq: [body.code, 0]           # 响应体里的 code 字段等于 0

  - name: 查询当前用户信息
    request:
        url: /api/user/info
        method: GET
        headers:
            Authorization: "Bearer $token"   # 用上一步提取的 $token
    validate:
        - eq: ["status_code", 200]
        - eq: [body.code, 0]
        - eq: [body.data.username, admin]
```

**关键点说明：**

- `config` 里只有 `name` 是必填，其余（`base_url`/`variables`/`verify`/`export`）都可选。
- `teststeps` 是列表，**从上到下顺序执行**，前面提取的变量（`$token`）后面可以直接用。
- `request` 里 `url` + `method` 是核心；`params`(URL 参数)、`headers`、`data`(表单/文本)、`json`(JSON 体)、`cookies`、`files`(上传)、`timeout`、`allow_redirects` 都可选。
- 变量引用用 `$变量名`；调用自定义函数用 `${函数名(参数)}`（函数写在同目录 `debugtalk.py` 里）。

### 1.3 这个工具能测什么、不能测什么

**✅ 能测（核心能力）：HTTP / HTTPS 接口**

- 所有 HTTP 方法：GET、POST、PUT、DELETE、PATCH、HEAD、OPTIONS
- 请求体类型：JSON、表单（form-urlencoded）、文本、multipart 文件上传
- 自定义 Header、Cookie、Session、`Authorization`（如 Bearer Token）；OAuth2 Client Credentials 内置
- 从响应提取变量并在步骤间传递（如先登录拿 token，再带 token 调接口）
- 参数化（`Parameters`）、前置/后置 hook（`debugtalk.py` 自定义函数）
- HTTPS 证书校验开关（`verify`）、超时、重定向控制、代理（`proxies`）、客户端证书（`cert`）
- 对响应做断言：**22 个内置算子**——状态码、响应体字段、响应头、长度、类型、正则、
  **响应元信息（耗时 `elapsed_ms`/`elapsed_s`、体积 `response_size`、`reason`）**、
  **结构/契约（`jsonschema_match`）**；断言算子还能在 `debugtalk.py` 里自定义
- **已有资产迁移**：`hconvert` 把 curl / HAR（浏览器录制）/ Postman 集合 / OpenAPI 契约转成 YAML 用例
- **测试数据管理**：`conftest.py` 夹具做环境准备与回收（见 6.2 的约定与示例）
- **CI 落地**：`--junitxml` + `--html` 报告、GitHub Actions / GitLab CI 模板

**❌ 不能测（默认能力之外）**

| 类型 | 原因 |
|---|---|
| WebSocket | 非 HTTP 协议，默认未实现 |
| gRPC / Thrift / RPC 私有协议 | 非 HTTP（源码有 `RunSqlRequest`/`RunThriftRequest` 雏形，但需额外依赖、非默认核心） |
| MQ（Kafka/RabbitMQ 等）、TCP/UDP | 非 HTTP |
| UI / 浏览器自动化 | 那是 Go 版 v5 的 `boom` 功能，**Python 版没有** |
| 数据库、移动端 App 原生 UI | 超出 HTTP 接口测试范围 |
| 性能压测 | 它是**功能测试**工具，不是专业压测工具 |

一句话：**只要被测对象是一个 HTTP(S) 接口，就能用；反之不能。**

## 第二步：命令行运行

三个命令的对应关系（源码 `interfacetester/cli.py` 里就是这么定义的）：

| 命令 | 等价于 | 作用 |
|---|---|---|
| `hrun test.yml` | `interfacetester run test.yml` | **转成 pytest 用例 + 直接运行**（最常用） |
| `hmake test.yml` | `interfacetester make test.yml` | **只转换**生成 pytest 用例，不运行 |
| `hconvert --from curl ...` | `interfacetester convert ...` | **把 curl / HAR / Postman / OpenAPI 转成 YAML 用例**（见 2.4） |
| `pytest xxx_test.py` | —— | 直接跑已生成的 pytest 用例 |

### 2.1 最常用：直接运行

```powershell
# 已激活 venv 的前提下
hrun testcase.yml                      # 运行单个用例
hrun testcases_dir/                    # 运行整个目录下的所有 YAML/JSON 用例
hrun test.yml -s                       # -s 显示打印输出（默认已开启）
hrun test.yml --html=reports/report.html --self-contained-html   # 同时生成 HTML 报告
```

`hrun` 会先做两件事：①把 YAML 转成 `xxx_test.py`；②用 pytest 跑这些 `_test.py`。

### 2.2 只转换不运行

```powershell
hmake testcase.yml
# 结果：同目录下生成 testcase_test.py（以及 __init__.py）
```

### 2.3 直接跑已转换的 pytest 用例

```powershell
pytest testcase_test.py -v
```

> ⚠️ 注意：`hmake`/`hrun` 最后会调 `black` 格式化生成的代码，**必须激活 venv**（`black.exe` 在 venv 里），否则报 `missing dependency tool: black`。

### 2.4 把已有资产转成用例：`hconvert`

如果接口已经在 **Postman / curl / 浏览器录制 / OpenAPI 契约**里存在，不用手抄成 YAML：

```powershell
# curl：一个文件里可以放多条命令（续行 \ 与 # 注释都支持）
hconvert --from curl    --in examples/data/curl/curl_examples.txt --out converted/

# HAR：浏览器 DevTools → Network → 右键 → Save all as HAR
hconvert --from har     --in demo.har                            --out converted/

# Postman：在 Postman 里导出 Collection v2.1
hconvert --from postman --in postman_collection.json             --out converted/

# OpenAPI / Swagger：契约 → 骨架用例
hconvert --from openapi --in petstore_demo.yaml                  --out converted/
```

**它会做什么**

| 行为 | 说明 |
|---|---|
| 生成**标准 YAML** | 与手写用例完全同构，之后照常用 `hrun` 跑、按需改 |
| **导出即验证** | 写完盘立刻 `load_testcase` + 渲染干跑 + 语法检查，通不过就报错（跑不通的产物不会留下来） |
| **敏感信息占位** | Cookie / Authorization / token 一律换成 `${...}`，值放 `config.variables`（默认从环境变量读），**明文不落 YAML** |
| **自动生成断言** | HAR / Postman 用录制或保存的示例响应、OpenAPI 用契约 schema → 状态码 + **JSON Schema**（`jsonschema_match`，走文件引用） |
| **分组** | Postman 按顶层 folder、OpenAPI 按 tag 各出一个用例文件；`--single-file` 可合并 |
| **降级告警** | 迁移不了的写法（Postman 的 JS 脚本、外部 `$ref`、未知动态变量…）会明确列出，`--report 报告.md` 可导出清单 |

**常用参数**

```powershell
hconvert --from postman --in c.json --out out/ --report out/import-report.md   # 附导入报告
hconvert --from openapi --in api.yaml --out out/ --include-tags pets --methods get,post
hconvert --from har --in demo.har --out out/ --exclude-hosts analytics.example.com
hconvert --from curl --in c.txt --out out/ --no-validate    # 跳过导出即验证（不推荐）
```

生成目录里会自动带一个 `debugtalk.py`（**项目标记**：框架靠它确定项目根目录，schema 文件引用就是相对它解析的），
以及 `schemas/*.json`（契约断言用）。

> 每种源支持哪些写法、哪些会被降级，逐条写在 **`docs/convert/README.md`**（**支持子集已冻结**，冻结是为了避免"看起来支持其实不支持"）。
> 导入后**一定要人工过一遍**：造出来的骨架值（路径 id、时间戳、示例值）需要按业务替换，断言的强弱也要自己补。

## 第三步：YAML 是怎么变成 pytest 的、怎么发请求、怎么断言

### 3.1 转换机制（hmake 做了什么）

`hmake test.yml` 的内部流程（源码 `interfacetester/make.py`）：

1. 读取 YAML/JSON，解析出 `config` + `teststeps`
2. 用 jinja2 模板（`__TEMPLATE__`）把用例**渲染成一个 pytest 文件** `test_test.py`
3. 调 `black` 格式化生成的代码
4. 顺手生成 `__init__.py` 让目录成为 Python 包

你上面那个 YAML 会被转成大致这样的 pytest 文件：

```python
# NOTE: Generated By InterfaceTester 4.3.5
from interfacetester import InterfaceTester, Config, Step, RunRequest

class TestCaseLogin(InterfaceTester):
    config = Config("登录并查询用户信息").base_url("http://your-server.com").verify(False)

    teststeps = [
        Step(
            RunRequest("登录获取 token")
            .post("/api/login")
            .with_headers(**{"Content-Type": "application/json"})
            .with_json({"username": "admin", "password": "123456"})
            .extract().with_jmespath("body.data.token", "token")
            .validate()
            .assert_equal("status_code", 200)
            .assert_equal("body.code", 0)
        ),
        Step(
            RunRequest("查询当前用户信息")
            .get("/api/user/info")
            .with_headers(**{"Authorization": "Bearer $token"})
            .validate()
            .assert_equal("status_code", 200)
            .assert_equal("body.code", 0)
            .assert_equal("body.data.username", "admin")
        ),
    ]

if __name__ == "__main__":
    TestCaseLogin().test_start()
```

**对照关系（YAML → pytest 链式写法）：**

| YAML 字段 | pytest 链式方法 |
|---|---|
| `request.method: GET` + `url` | `.get("/path")` |
| `request.method: POST` | `.post("/path")` |
| `params` | `.with_params(**{...})` |
| `headers` | `.with_headers(**{...})` |
| `data` | `.with_data("...")` |
| `json` | `.with_json({...})` |
| `extract: - name: path` | `.extract().with_jmespath("path", "name")` |
| `validate` | `.validate().assert_xxx(...)` |

### 3.2 怎么发 HTTP 请求

- 底层用 Python 的 **`requests`** 库（`interfacetester/utils.py` 里 `import requests`，响应头 `user-agent` 默认就是 `python-requests`）。
- 执行器是 `SessionRunner`（`interfacetester/runner.py`）：每个用例一个实例，`test_start()` 被 pytest 发现后，**从上到下依次执行每个 Step**。
- 每个 Step 内部调用 `requests.request(method, url, ...)` 发出真实 HTTP 请求，拿到 `Response` 对象后做提取和断言。

> ⚠️ **`data` 与 `json` 不能同时写在同一个 `request` 里**（批次 B / M6 起会**响亮报错**）。
> requests 的实际行为是「`data` 非空时**整个 `json` 分支不执行**」，也就是 `json` **被静默丢掉**：
> 实测 YAML 里写 `data: "a=1&b=2"` + `json: {k: v}`，服务端只收到 `a=1&b=2`，
> 而 `hmake` 与运行期**零告警**（两个键都是正式字段，未知字段告警不会响）——
> 请求体与用例里写的不一致却看不出来。
> 要发 JSON 体就删掉 `data:`，要发文本/表单体就删掉 `json:`；
> **URL 查询串请用 `params:`**（`data:` 是请求体，这是最常见的混淆点）。
>
> ⚠️ **一个 step 只能是一种类型**（批次 B / M2 起报错）：`request` 与 `testcase` 不能并存
> （v2/v3 的 `api:` 也算 `testcase`）。修复前那种写法会让**整条引用用例被静默丢弃** ——
> 被引用的接口一次都不跑（它内部的断言自然也不跑），父用例照样变绿。
> 要「先调子用例、再打主接口」就**拆成两个 step**。
>
> ⚠️ **HTTPS 默认不校验证书**（`verify` 的默认值是 `False`，沿用上游取向）：框架在 import 期
> 就关掉了 `InsecureRequestWarning`，所以**证书错误（自签名/过期/中间人）不会被发现**。
> 批次 C / M5 起每次运行会**提示一次**（每个进程），要校验证书请写 `config: {verify: true}`
> 或在该 step 写 `request: {verify: true}`（step 级优先）。测生产地址时请务必打开。
>
> ⚠️ **数值断言两侧都是字符串时是「字典序」比较**：`greater_than: ["body.price", "100"]`
> 在接口把数字返回成字符串时会因 `"9" > "100"` 而**通过**（字典序里 `'9' > '1'`）。
> 批次 C / L11 起会**告警**说明这一点；比数值请把期望值写成**数字**（`100` 而不是 `"100"`），
> 并确认 check 侧取到的也是数字。只在比日期串/版本串时才应保持字符串（字典序恰好等于你要的序）。
>
> ⚠️ **源文件名/目录名会成为 Python 标识符**（批次 B / M1）：`-`/`.`/空格 折成 `_`，
> 其它不能出现在标识符里的字符（`+ @ & ' ( ) ! % , ; = [ ] ^ ` { } ~ $ #`）与关键字也会被折/挡掉，
> 数字开头的段补 `T`。所以 `case+1.yml` 生成的是 `case_1_test.py` / `class TestCaseCase1`。
> 修复前这类名字会让 `hmake` **退出码 0** 却产出语法错误的文件（直到 `hrun` 才报
> `collected 0 items / 1 error`），`hconvert` 侧还会因为合法的 Postman folder 名（`Auth + Token`）整体失败。

### 3.3 怎么断言

断言写在各步骤的 `validate` 里，格式统一为：

```yaml
validate:
    - 比较方式: [检查项, 期望值]        # 可选第三项是自定义错误提示
    - eq: ["status_code", 200]
    - eq: [body.code, 0, "code 应该等于 0"]
```

**① 检查项（check）：断言"看哪里"**

| 检查项 | 含义 |
|---|---|
| `status_code` | 响应状态码 |
| `body` / `body.字段路径` | 响应体（JSON，用 jmespath 取子字段） |
| `headers.字段` | 响应头 |
| `cookies.字段` | 响应 Cookie |
| `elapsed` | 响应耗时 |
| `content` | 原始字节内容 |

jmespath 取字段举例：`body.data.token`（嵌套）、`body.items[0].name`（数组）、`body.headers.Host`（含特殊字符的键用双引号包住，如 `body."user-agent"`）。

> ⚠️ **字段名里有 `-` 就必须加双引号**（0918-8 / M32）：`-` 在 jmespath 里是运算符，
> 写 `headers.X-Trace` 会直接抛 `Bad jmespath expression: Unknown token '-'`；
> 正确写法是 `headers."X-Trace"`。`content.xxx` / `json.xxx` 这类 **v2/v3 旧写法**由兼容层
> 自动改写（连 `headers.X-Trace` 一起，会自动补引号）；v4 写法请自己加引号。

**② 比较方式（assert）：断言"怎么比"**（常用，源码 `interfacetester/response.py`）

| 写法 | 含义 | 别名 |
|---|---|---|
| `eq` | 相等 | equals / equal |
| `ne` | 不相等 | not_equal |
| `lt` / `le` | 小于 / 小于等于 | less_than / less_or_equals |
| `gt` / `ge` | 大于 / 大于等于 | greater_than / greater_or_equals |
| `str_eq` | 字符串相等 | string_equals |
| `len_eq` / `len_gt` / `len_lt` | 长度相等/大于/小于 | length_equal 等 |
| `startswith` | 以…开头 | — |
| `endswith` | 以…结尾 | — |
| `contains` | 包含 | — |
| `regex_match` | 正则匹配 | — |
| `type_match` | 类型匹配（如 "None"、"int"） | — |

对应 pytest 链式写法就是 `.assert_equal(...)`、`.assert_startswith(...)`、`.assert_length_equal(...)`、`.assert_type_match(...)` 等。

## 第四步：HTML 测试报告

### 4.1 怎么生成

**interfacetester 默认不自动生成 HTML 报告**——`hrun test.yml` 只在终端打印 pytest 结果。要生成报告，显式加 `--html` 参数（interfacetester 已内置 `pytest-html`）：

```powershell
hrun test.yml --html=reports/report.html --self-contained-html
```

- `--html=路径`：指定报告输出文件（建议放 `reports/` 目录）
- `--self-contained-html`：把 CSS/JS 内嵌进单个 html 文件，**双击就能离线打开**，不依赖外部资源（推荐加）
- 也可以加 `--junitxml=reports/junit.xml` 同时产出 JUnit XML（便于 CI 集成）

### 4.2 报告文件的结构（浏览器打开后从上到下）

报告由 `pytest-html` 生成，是一个**可交互的单页 HTML**，结构如下：

1. **标题 + 生成信息**
   - 报告标题（默认是文件名，如 `report.html`）
   - 生成时间、由 `pytest-html` vX.X 生成

2. **Environment 环境信息表**
   - 运行环境快照：Python 版本、操作系统平台、pytest 及插件版本等

3. **Summary 汇总区（最重要）**
   - `总用例数`、`通过(passed)`、`失败(failed)`、`错误(error)`、`跳过(skipped)`、`总耗时`
   - 顶部还有一条「通过率」进度条，绿=通过、红=失败

4. **Results 结果列表**
   - 每个测试用例一行，显示：状态图标（✅/❌/⏭）、用例名、耗时
   - **可点击展开**该用例详情：测试步骤、日志输出、提取的变量、请求/响应摘要

5. **失败用例的详情（重点看这里）**
   - 展开失败用例，能看到**断言失败的具体信息**：实际值 vs 期望值
   - 例如 `assert body.code == 0`，实际返回 `500`，会清晰标出差异
   - 还有堆栈信息，便于定位是哪一步、哪个断言挂了

### 4.3 报告长什么样（示意）

```
┌─────────────────────────────────────────────┐
│  report.html                     pytest-html │
│  Report generated on 2026-09-15 ...         │
├─────────────────────────────────────────────┤
```

| 步骤 | 干什么 | 核心命令/文件 |
|---|---|---|

## 进阶：参数化 + 自定义函数 debugtalk.py

### 5.1 自定义函数 debugtalk.py

**它是什么**：一个普通的 Python 文件，放在**测试用例目录（或其上层，interfacetester 会自动向上找项目根目录）**。里面定义的任何 Python 函数，都能在 YAML 里用 `${函数名(参数)}` 调用。常见用法：动态生成时间戳/随机串、封装签名算法、统一拿 token 等。

**示例 `debugtalk.py`：**

```python
import time
import random
import string

def get_timestamp():
    """当前时间戳"""
    return int(time.time())

def gen_random_string(length=8):
    """生成指定长度的随机字符串"""
    return "".join(
        random.choice(string.ascii_letters + string.digits) for _ in range(length)
    )

def sum_two(m, n):
    """求和"""
    return m + n
```

**在 YAML 里调用：**

```yaml
config:
    name: 使用自定义函数
    base_url: http://your-server.com

teststeps:
  - name: 动态参数
    request:
        url: /api/list?_t=${get_timestamp()}          # 函数拼进 URL
        method: GET
        headers:
            X-Nonce: ${gen_random_string(16)}         # 带参数的函数
        json:
            total: ${sum_two(1, 2)}                   # 传位置参数
    validate:
        - eq: ["status_code", 200]
```

**语法规则（源码 `parser.py` 正则确认）：**

| 写法 | 含义 |
|---|---|
| `$var` / `${var}` | 引用变量 |
| `${func()}` | 调用函数（无参） |
| `${func(1, 2)}` | 位置参数 |
| `${func(a=1, b=2)}` | 关键字参数 |
| `$$` | 转义，表示字面量 `$` |

**函数查找顺序**（找不到就报错）：先查 `debugtalk.py` → 再查 interfacetester 内置函数 → 最后查 **Python 内置函数**（所以 `len`/`str`/`int` 等可直接用）。

**内置函数（无需自己写）：**

- `${parameterize(文件名.csv)}`（别名 `P`）：读 CSV 文件（参数化用）
- `${environ(变量名)}`（别名 `ENV`）：读系统环境变量，如 `${ENV(PATH)}`

### 5.2 参数化 Parameters（数据驱动）

**作用**：一条用例自动跑多组数据。

**原理**：YAML 的 `config` 里加 `parameters` 字段，`hmake` 会把它转成 pytest 的 `@pytest.mark.parametrize("param", Parameters(...))`（源码 `make.py` 确认）；多组参数之间做**笛卡尔积**。

**三种数据来源：**

**① 直接写列表（单参数）**

```yaml
config:
    name: 参数化示例
    base_url: http://your-server.com
    parameters:
        user_agent: ["iOS/10.1", "iOS/10.2", "iOS/10.3"]

teststeps:
  - name: 用参数发请求
    request:
        url: /api/ua
        method: GET
        headers:
            User-Agent: $user_agent          # 引用参数变量
    validate:
        - eq: ["status_code", 200]
```

**② CSV 文件（多参数，参数名用 `-` 连接）**

```yaml
config:
    parameters:
        username-password: ${parameterize(account.csv)}   # 两个参数：username / password
```

`account.csv`（放项目根目录，即 `debugtalk.py` 同级）：

```csv
username,password
user1,111111
user2,222222
```

> ⚠️ **多参数时：参数名个数与取值个数必须相等**（0918-8 / L20 起明确报错）。
> 参数名用 `-` 分隔（`username-password` 是 2 个名字），每个取值也要给出同样多个：
> `[["user1", "111111"]]` ✅；`[[1, 2]]`（名字只有 1 个）❌、`[[1]]`（名字 2 个、值 1 个）❌。
> 修复前 `dict(zip(...))` 会把**多出来的值静默丢掉**——生成出来的用例与你写的不是同一个用例，却照样全绿。

**③ debugtalk.py 函数返回数据**

```yaml
config:
    parameters:
        app_version: ${gen_app_version()}
```

对应的 `debugtalk.py`（返回字典列表或元组列表）：

```python
def gen_app_version():
    return [{"app_version": "2.8.5"}, {"app_version": "2.8.6"}]
```

**pytest 风格等价写法：**

```python
import pytest
from interfacetester import InterfaceTester, Config, Step, RunRequest, Parameters

class TestCaseParam(InterfaceTester):
    config = Config("参数化").base_url("http://your-server.com")
    teststeps = [
        Step(RunRequest("...").get("/api/ua").validate().assert_equal("status_code", 200))
    ]

    @pytest.mark.parametrize(
        "param",
        Parameters({"username-password": [["user1", "111111"], ["user2", "222222"]]}),
    )
    def test_start(self, param):
        super().test_start(param)
```

> **数据集为空会报错（批次 A / H2，行为扩张）**：`parameters: {uid: []}`、
> **只有表头**的 CSV、`${func()}` 返回 `[]`——这些都会被**响亮拒绝**并点名是哪个参数
> （报错里带取值来源），而不是"跑 0 次、看起来是绿的"。
> 修复前它返回空列表 → `@pytest.mark.parametrize("param", [])` → pytest 判 **skip**
> （不是 failed）→ `hrun` **exit 0**、零告警。而「数据集为空」几乎总是
> 环境/数据问题的征兆（查库为空、CSV 还没填、ENV 指错），**不能**被伪装成"跑过了"。
> 与上面 ① 的「长度不匹配必须报错」是同一条口径（L20），只是「长度 = 0」以前被漏掉了。
> `parameters: {}`（**没有**参数化）不受影响。

### 5.3 hook：前置 / 后置钩子

**作用**：在**发请求前**或**发请求后**执行自定义逻辑——比如改请求头、加签名、记录日志、改响应等。

**写在 request 步骤里：**

```yaml
teststeps:
  - name: 带 hook 的请求
    request:
        url: /api/order
        method: POST
        json: {}
    setup_hooks:                          # 发请求前执行
        - ${setup_hook_add_header($request)}
    teardown_hooks:                       # 发请求后执行
        - ${teardown_hook_log($response)}
    validate:
        - eq: ["status_code", 200]
```

**对应的 `debugtalk.py`：**

```python
def setup_hook_add_header(request):
    """setup hook 接收 request 参数，可直接修改请求"""
    request["headers"]["X-Extra"] = "hello"

def teardown_hook_log(response):
    """teardown hook 接收 response 参数，可读取响应"""
    print("status:", response.status_code)
```

**hook 的执行顺序（源码 `step_request.py` 确认）：**

```
解析请求 → 设置 $request 变量 → setup_hooks → 发出请求
        → 设置 $response 变量 → teardown_hooks → extract → validate
```

**hook 的两种写法：**

| 写法 | 含义 |
|---|---|
| `- ${func()}` | 只调用函数，不管返回值 |
| `- 变量名: ${func()}` | 把函数返回值赋给变量 `$变量名` |

**两个特殊变量：**

- `$request`：setup hook 里可访问，是解析后的请求 dict（改它 = 改实际发出的请求）
- `$response`：teardown hook 里可访问，是响应对象（有 `.status_code`、`.body`、`.headers` 等属性）

> 命名惯例：`debugtalk.py` 里的 hook 函数通常以 `setup_hook_` / `teardown_hook_` 开头，方便区分（并非强制）。

### 5.4 超时怎么配（request / config / 环境变量）

请求超时按下面的顺序生效（左边优先），三层都不配时用框架默认值 **120 秒**：

| 层级 | 写法 | 适用场景 |
|---|---|---|
| step 级 | `request.timeout: 5`（或链式 `.set_timeout(5)`） | 某个接口特别慢/特别快，单独指定 |
| 用例级 | `config.timeout: 30`（或链式 `Config("...").timeout(30)`） | 本用例内所有请求统一超时 |
| 环境级 | 环境变量 `INTERFACETESTER_TIMEOUT=5` | CI 上整体调短，YAML 一个字都不用改 |
| 默认 | **120 秒**（框架内置，本次未改动） | 以上都未配置时 |

```yaml
config:
    name: 超时示例
    base_url: ${ENV(BASE_URL)}
    timeout: 30            # 用例级：本用例所有请求 30s 超时

teststeps:
  - name: 慢接口单独放宽
    request:
        url: /api/export
        method: POST
        timeout: 300       # step 级：覆盖 config 的 30s
    validate:
        - eq: ["status_code", 200]
```

```powershell
# 环境级：CI 上整体调短，YAML 不用改
$env:INTERFACETESTER_TIMEOUT = "5"; hrun testcases/
```

三点注意：

- 超时值必须是数字；`${ENV(...)}` 解析出来是字符串，框架会自动转成数字；写错（如 `timeout: abc`）会直接报 `ParamsError`，不会被拖到发请求时才炸。
- `timeout: 0` 表示「立即超时」（常用于只验证连通性），是**合法值**，不会被当成「未设置」而回落默认值。
- 配置了 `config.timeout` 时，OAuth2 取 token 的请求也用它；未配置时 token 请求固定用 30s（比业务请求短，避免卡在认证上）。

### 5.5 文件上传（multipart/form-data）

**前提**：先安装 `upload` 扩展（`python -m pip install -e ".[upload]"`，见 `docs/deploy.md` 第 6 节），否则运行时会报依赖缺失。

**作用**：通过 `request.upload` 字段发送 `multipart/form-data`，常用于上传文件。文件字段的值写**本地文件路径**，普通表单字段直接写值即可；框架会自动探测文件 MIME 类型并生成 `boundary`（不要手写 `Content-Type: multipart/form-data`）。

```yaml
config:
    name: 上传文件
    base_url: http://your-server.com
    verify: false

teststeps:
  - name: 上传文件
    request:
        url: /api/file/upload
        method: POST
        upload:
            path: /app-xxx/                    # 普通表单字段：目标目录
            files: test_files/测试文件.txt       # 文件字段：本地文件路径（支持中文文件名）
    validate:
        - eq: ["status_code", 200]
        - eq: [body.success, true]
```

**要点**：

- `upload` 里每个键值对是一个表单字段：值指向本地文件路径时按文件上传，其余按普通文本字段处理。
- 中文文件名按 UTF-8 编码上传，框架内置处理，不会触发 `UnicodeEncodeError`。
- 可配合 `x_path`（业务需要 `X-Path` 请求头时）与 `config.oauth2` 自动认证一起用，完整示例见 `examples/unifsp/file_upload.yml`。
- 转换后的 pytest 链式写法等价于 `RunRequest("...").post("/api/file/upload").upload(**{"path": "...", "files": "..."})`。

### 5.6 SQL 请求（RunSqlRequest）

**前提**：先安装 `sql` 扩展（`python -m pip install -e ".[sql]"`，即 `sqlalchemy` + `pymysql`，见 `docs/deploy.md` 第 6 节）。

**作用**：在用例里执行 SQL，用于测试前**造数据**、测试后**清理数据**，或验证「接口写入是否真的落库」。它不是被测的 HTTP 接口，而是辅助步骤。

> ⚠️ 注意：`RunSqlRequest` 目前**只能通过 pytest 风格的 Python 用例**（`_test.py`）直接写，**不支持在 YAML 里写 `sql_request:` 字段 + `hmake` 转换**（`hmake` 只识别 `request` / `testcase` 两种 step）。

**最简写法（连接信息写在 step 上）：**

```python
from interfacetester import InterfaceTester, Config, Step, RunSqlRequest

class TestCaseSql(InterfaceTester):
    config = Config("SQL 造数与校验")

    teststeps = [
        Step(
            RunSqlRequest("查询单条")
            .with_db_config(ip="127.0.0.1", port=3306, user="root",
                            password="123456", database="test_db")
            .fetchone("SELECT id, name FROM t_user WHERE id = 1")
            .extract()
            .with_jmespath("name", "user_name")          # 单行结果用字段名直接取
            .validate()
            .assert_equal("id", 1)
        ),
    ]

if __name__ == "__main__":
    TestCaseSql().test_start()
```

**`method` 支持 6 种**（源码 `models.py` 的 `SqlMethodEnum`），对应链式方法：

| 链式方法 | 含义 | 结果形态 |
|---|---|---|
| `.fetchone(sql)` | 查询单条 | 单行 dict，用 `字段名` 提取 |
| `.fetchmany(sql, size)` | 查询多条（限制条数） | 行列表，用 `[0].字段` 提取 |
| `.fetchall(sql)` | 查询全部 | 行列表，用 `[0].字段` / `@` 提取 |
| `.insert(sql)` / `.update(sql)` / `.delete(sql)` | 增 / 改 / 删 | 影响行数 |

> ⚠️ **`fetchmany` 的 `size` 必须 ≥ 1**（0918-8 / L23 起明确报错）。YAML 里忘写 `size`
> 时模型默认是 `0`，修复前会**静默返回 `None`**（看起来像「查不到数据」，实际是参数写错）。
> 取单行用 `fetchone`，取全部用 `fetchall`。
>
> ⚠️ **返回形态与语句分类**（0918-8 / M26、M27）：
> ① `fetchmany` 无论 `size` 是几都返回**行列表**（修复前 `size=1` 返回 dict，与上表矛盾）；
> ② 是否「有结果集」按 SQLAlchemy 的 `returns_rows` 判断，不再看 SQL 的前 6 个字符——
> `WITH … AS (…) SELECT …`（CTE）与带前导注释的查询都能正常返回，
> `REPLACE INTO` / `TRUNCATE` / `CREATE` 等写库语句**一定会提交**（修复前不提交 → 写入被回滚）；
> ③ 结果集里的**字符串列不会被改类型**：只有解析结果是 dict/list 的 JSON 列才会被转成对象，
> 修复前 `"123"` 会变 `int`、`"1.10"` 会变 `1.1`，断言与引用会跟着被污染。

**提取与断言的 jmespath 规则**（结果被包成 `SqlResponseObject`，直接对原始结果做 jmespath）：

```python
# fetchall 返回列表：[{"name": "alice"}, {"name": "bob"}]
Step(
    RunSqlRequest("查询全部")
    .fetchall("SELECT name FROM t_user")
    .extract()
    .with_jmespath("[0].name", "first_name")     # 取第一行的 name
    .validate()
    .assert_equal("[0].name", "alice")
    .assert_length_equal("@", 2)                 # "@" 表示整个结果集
)
```

**另一种配置连接的方式：注入外部引擎**（适合测试前用 `DBEngine` 自行建连，或连接信息复杂时）：

```python
from interfacetester.database.engine import DBEngine

class TestCaseSql(InterfaceTester):
    config = Config("注入引擎")
    teststeps = [Step(RunSqlRequest("查询").fetchall("select * from t_user"))]

    def test_start(self):
        self.with_db_engine(DBEngine(db_uri="mysql+pymysql://root:pw@127.0.0.1:3306/test_db"))
        super().test_start()
```

（完整可跑示例见 `examples/sql/test_sql_demo.py`。）

**要点**：

- 同一用例内若 `db_config` 发生变化（换库/换主机），框架会自动关闭旧连接并按新配置重建（源码 `step_sql_request.py`）。
- 用例结束时框架会自动释放数据库连接，无需手动 `close()`。
- step 内 hook 可通过 `$sql_response` 读取结果（是包装对象，取原始结果用 `.resp_obj` 或 `.extract()`）。
- 账号/口令里可以直接写**特殊字符**（空格、`@`、`%`、`/`、`:`、中文…）：框架按「连接串的消费者（SQLAlchemy）怎么解」来编码，`password="p@ss word"` 就是拿这个口令去连。批次 D / T4 修复前用的是 `quote_plus`，口令里的**空格**会被编成 `+`、而 SQLAlchemy **不**把 `+` 还原成空格 → 等于拿**被改过的口令**去连，现象是「认证失败，但 YAML 里写的口令是对的」。库名不做编码（写 `my db` 就传 `my db`）。

### 6.1 契约断言：`jsonschema_match`（第 19 个内置算子）

逐字段断言（`eq`）只能盖住你想到的字段；**契约级断言**能一次性盖住「结构 + 类型 + 必填 + 枚举」，
接口新增/删除字段、改类型这类问题都会被抓到。

```yaml
config:
    name: 用户详情契约
    base_url: https://your-api.example.com
teststeps:
    - name: 断言响应符合契约
      request:
          method: GET
          url: /users/1
      validate:
          - eq: ["status_code", 200]
          # 写法一（首选）：schema 放 debugtalk.py，用函数返回
          - jsonschema_match: ["body", "${get_user_schema()}"]
          # 写法二（次选）：schema 文件路径（相对项目根目录 = 含 debugtalk.py 的那层）
          # - jsonschema_match: ["body", "schemas/user.json"]
```

`debugtalk.py` 里：

```python
USER_SCHEMA = {
    "$schema": "https://json-schema.org/draft/2020-12/schema",
    "type": "object",
    "required": ["code", "data"],
    "properties": {
        "code": {"type": "integer"},
        "data": {
            "type": "object",
            "required": ["id"],
            "properties": {"id": {"type": "string"}},
        },
    },
}


def get_user_schema():
    return USER_SCHEMA
```

**要点**

- **带 `$` 键的 schema 不能内联**：`$schema`/`$ref` 这些 `$` 开头的键会被框架当成变量解析（运行期报 `VariableNotFound`）。
  写 `validate: - jsonschema_match: [body, {"$schema": ...}]` 会在 `hmake` 阶段**直接报错**并提示两种正确写法。
  不含 `$` 键的极简内联 schema 仍可用。
- **两种引用方式**：`${func()}` 返回值（首选）、schema 文件路径（`.json`/`.yaml`，相对项目根目录解析）。
- **失败信息是给人看的**：每条给出「出错路径（`$.data.items[0]`）+ 期望（关键字/期望值）+ 实际值(类型)」，
  最多 5 条并提示省略了几条；schema 里写 `description` 会一并带上；第三个参数可加自定义说明（前置显示）。
- **区分「断言失败」和「环境/用法错误」**：校验不通过 = 断言失败（JUnit 记 `failed`）；
  schema 文件找不到、schema 本身不合法、`jsonschema` 缺失 = 报错并给可操作提示。
- draft：schema 写了 `$schema` 就按它选，否则用 Draft 2020-12，失败信息里会标出实际使用的 draft。

> 更细的说明见 `docs/能力清单.md` 的「JSON Schema 断言」一节。

### 6.2 测试数据管理：造数、隔离、回收

接口自动化最容易烂在「数据」上：用例之间互相污染、跑完不清理、换个人跑就失败。
`examples/data_management/` 给出一套**可跑**的约定（T1~T5），核心就三条：

1. **夹具只能「准备/回收环境」，不能给用例传值**（框架生成的用例签名固定、只有 `autouse=True` 的夹具生效）
   → 要传值就写 `os.environ`，再由 `debugtalk.py` 的函数读出来；
2. **数据名带前缀**：`<运行前缀>-<用例前缀>-<业务后缀>` —— 查询按前缀、回收按前缀，永远不用「清空全库」；
3. **造数与回收成对发生**：造数函数内部就把回收动作登记好，用例结束时统一执行（清理失败**只告警不阻断**）。

```powershell
hrun examples/data_management              # 正常：4 passed, 1 skipped
$env:DM_DISABLE_CLEANUP='1'                # 故意关掉回收 → 能看到「数据污染」把用例打红
hrun examples/data_management/02_isolation_check.yml
$env:DM_ENV_NAME='prod'                    # 生产环境：危险操作被强制跳过（3 passed, 2 skipped）
hrun examples/data_management -q -rs
```

> 完整说明（含环境矩阵 `.env` 的坑）见 `examples/data_management/README.md`。

### 6.3 接到 CI

仓库自带两个平台的模板，开箱可用：

```bash
# GitHub Actions：unit-test（排除外网用例）+ network-tests（非阻塞）+ examples-smoke
.github/workflows/test.yml

# GitLab CI：同样的三个 job
.gitlab-ci.yml
```

**CI 上必须知道的几件事**（详见 `docs/ci/README.md`）：

- **80/443 是特权端口**：非 root 的 runner 绑不上，用环境变量把本地 mock 端口调大即可
  （`INTERFACETESTER_HTTP_BIN_PORT=8000`、`INTERFACETESTER_HTTPS_BIN_PORT=8443`，用例里的地址会自动跟着变）；
- **有 6 个用例依赖公网 `postman-echo.com`**（抖动时以 120s 读超时失败）→ 主 job 用 `--deselect` 排除它们，
  另设一个**非阻塞** job 单独跑，既保证主 job 稳定又不丢信号；
- **报告**：`--junitxml`（平台聚合）+ `--html --self-contained-html`（给人看，单文件）；
- **内网离线**：按 `requirements.txt` 预下 wheel；注意 `jsonschema` 的传递依赖 `rpds-py` 是二进制包，要下对应平台的 wheel。

### 6.4 测 SOAP/XML 接口

存量系统里还有不少 SOAP/XML 接口。**请求照发**（`data` 传 XML + `headers` 配
`Content-Type`/`SOAPAction`），但断言有个坑要先知道：

> XML 响应的 `body` 不是 JSON → 框架取到的是 **bytes**，
> `contains` / `regex_match` / `startswith` 在它上面**用不了**
> （`contains` 会直接抛 `TypeError: a bytes-like object is required, not 'str'`）。

补齐方式有**两种形态**（算子名相同、YAML 写法相同，差别在「谁提供实现」）：

| | A1：项目级算子（`examples/soap/debugtalk.py`） | A2-1 + A2-2：框架内置算子 |
| --- | --- | --- |
| 怎么用 | 把那四段算子**复制进自己项目的 `debugtalk.py`** | 直接用，不复制任何代码 |
| 依赖 | **零新增**（标准库） | `pip install -e ".[xml]"`（lxml，二进制依赖） |
| 选择器 | 简化写法：`code` / `{URI}code` / `item[@id='1']` | 简化写法 **+ 完整 XPath 1.0**（`text()`/`count()`/`string()`/位置谓词/轴/多级路径） |
| **XSD 契约校验** | ❌ | ✅ `xml_schema_match`（A2-2）：**先定位业务元素再校验** |
| 项目里已有同名算子时 | 用它自己那份（**项目优先**，内核算子被遮蔽） | 需删掉/改名项目里的同名算子才会接管 |

> 两种都不改 YAML 书写方式 —— 所以可以先按 A1 起步，等能装 lxml 时**删掉 `debugtalk.py` 里的同名算子**
> 就自动升级到内核实现（既有断言语义完全不变）。

```yaml
teststeps:
-
  name: 查询（含错误分支）
  request:
    method: POST
    url: /svc/query
    headers:
      Content-Type: "text/xml; charset=utf-8"
      SOAPAction: "urn:your#Query"
    data: "$envelope"          # XML 报文，可直接写 ${var}
  validate:
    - equal: ["status_code", 500]                 # ← SOAP 的业务错误也是 HTTP 500
    - soap_fault: ["body", "Invalid parameter"]   # 断 Fault 内容，而不是「服务挂了」（A1 示例提供的专用算子）
    - xpath_match: ["body", ["code", "0000"]]     # 命名空间前缀漂移（ns1:/abc:）都能断
    - xpath_match: ["body", "//ns1:code/text()"]  # 原始 XPath：只有内核算子支持（A2-1）
    - xpath_count: ["body", ["item", 3]]          # 明细条数
    # XSD 契约（A2-2）：契约里写过的约束，用例里不必重复
    - xml_schema_match: ["body", {"xpath": "QueryResponse", "xsd": "schemas/query.xsd"}]
```

五个必须知道的点：

- **业务错误也是 HTTP 500**：照 REST 模板写 `equal: ["status_code", 200]` 会把「参数校验失败」
  误报成「接口挂了」；
- **命名空间前缀漂移**：同一份契约在不同环境可能是 `ns1:`/`abc:`/`soap:`，**简化写法**按 local-name 选节点，
  所以断得住；需要精确限定就用 `{命名空间URI}节点名`；
- **原始 XPath 里的前缀是字面量**：报文把 URI 声明成 `abc:` 时，`//ns1:code` 会直接报
  `Undefined namespace prefix`（要「不管前缀」就写 `//*[local-name()='code']`，或用简化写法）；
  另外**默认命名空间**（`xmlns=` 无前缀）没法用 XPath 前缀，也只能靠 `local-name()` / 简化写法；
- **XSD 契约校验要先定位**：客户 XSD 通常只描述 Body 里那层元素，所以写
  `{"xpath": "QueryResponse", "xsd": "schemas/query.xsd"}`（直接校验整个 Envelope 会报
  `No matching global declaration`）；XSD **只能是文件路径**（`xs:include` 要按文件所在目录解析），
  相对路径按项目根目录解析；**前缀漂移不影响 XSD 校验**（它按 URI 匹配），但 XSD 必须声明对应的 `targetNamespace`；
  路径写错会在 `hmake` 阶段就报出来；
- **报文不合法要报错**，不要静默放过：非法 XML 会以「响应体不是合法 XML」（A1 走 ElementTree 时文案是
  `unbound prefix`，内核走 lxml 时是 `Namespace prefix … is not defined`）失败。

**断简单字符串片段**：不要写在 `body` 上（它是 bytes，会报类型错），写在 **`text`** 上：

```yaml
  validate:
    - type_match: ["body", bytes]                        # body = 原始字节
    - contains: ["text", "<ns1:code>0000</ns1:code>"]    # text = 解码后的字符串
    - startswith: ["text", "<?xml"]
```

**要从 XML 里取值给后续步骤用**（多步 SOAP 链路）：`extract` 只认 jmespath，对 XML 的
`body.code` 会报错（修复前是静默 `None`），请用 `teardown_hooks`（**复数**！单数会被静默忽略、钩子不执行）：

```yaml
  teardown_hooks:
    - code: "${xml_field($response, code)}"        # 本步骤内可用 $code（参数不加引号）
    - ${capture_xml($response, $soap_capture)}     # 写 os.environ，供后续步骤 ${ENV(...)} 读
```

完整示例见 `examples/soap/chain.yml`；四条实测规则与坑见 `docs/soap/README.md`「XML 取值与多步链路」。

```bash
# 可离线跑通的完整示例（各自带本地 mock）
python -m interfacetester run examples/soap         # A1 项目级算子，零依赖 → 期望 3 passed, 1 skipped
pip install -e ".[xml]"                             # A2-1/A2-2 内核算子需要 lxml
python -m interfacetester run examples/soap_xpath   # 内核算子（XPath + XSD）→ 期望 2 passed, 2 skipped
```

细节（SOAP 1.1/1.2 模板、Fault 模板、选择器限制、XSD 六条规则、两种写法的取舍、存量 SoapUI/HAR 迁移）见
`docs/soap/README.md`、`examples/soap/README.md`（A1 算子用法）与
`examples/soap_xpath/README.md`（内核算子、XSD 契约校验与两种写法对照）。

## 进阶回顾

| 需求 | 用什么 |
|---|---|
| 动态生成时间戳/随机串/签名/拿 token | `debugtalk.py` 里写函数，YAML 用 `${func()}` 调用 |
| 一条用例跑多组数据 | `config.parameters`（列表 / CSV / debugtalk 函数） |
| 发请求前改请求、发请求后处理响应 | 步骤里的 `setup_hooks` / `teardown_hooks` |
| 读环境变量 / 读 CSV | 内置 `${ENV(名)}` / `${parameterize(文件.csv)}` |
| 上传文件（multipart） | `request.upload`（需装 `upload` 扩展，见 5.5） |
| 造数 / 清理 / 校验数据库 | Python 用例里的 `RunSqlRequest`（需装 `sql` 扩展，见 5.6） |
| **断言响应结构/契约** | **`jsonschema_match`**（见 6.1；schema 走 `${func()}` 或文件路径，内联仅限不含 `$` 键的极简 schema） |
| **测试数据造数/隔离/回收** | 照 `examples/data_management/` 的约定（见 6.2） |
| **把 Postman/curl/HAR/OpenAPI 变成用例** | `hconvert --from …`（见 2.4） |
| **接 CI / 出报告 / 离线部署** | `.github/workflows/test.yml`、`.gitlab-ci.yml`（见 6.3 与 `docs/ci/README.md`） |
| **测 SOAP/XML 接口** | 请求照发；断言用**内置** `xpath_match`/`xpath_count`/`xml_schema_match`（A2-1/A2-2，需 `xml` extra，完整 XPath 1.0 + XSD 契约校验）或 `examples/soap/` 的项目级算子（A1，零依赖退路）（见 6.4 与 `docs/soap/README.md`） |
| 变量引用 / 函数转义 | `$var` / `${func()}` / `$$` |

**记住一条主线**：`debugtalk.py` 定义逻辑 → YAML 里用 `${函数()}` 和 `$变量` 引用 → interfacetester 运行时用 `requests` 发请求、按 `validate` 断言。
