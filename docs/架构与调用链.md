# InterfaceTester 架构与调用链

> **本文档回答三个问题**：① 一个 YAML 用例从磁盘到报告，代码到底走了哪些函数？
> ② 出问题时该看哪个模块？③ 框架在哪些位置**主动拦截「假通过」**（用例绿了但实际什么都没校验）？
>
> 适用范围：本仓库当前状态（`interfacetester/` 34 个模块、约 1.8 万行；`tests/` 约 2.9 万行）。
> 与本文档配套的文档：能力边界看 [`能力清单.md`](能力清单.md)，导入器看 [`convert/README.md`](convert/README.md)，
> SOAP 看 [`soap/README.md`](soap/README.md)，CI 看 [`ci/README.md`](ci/README.md)。

## 〇、怎么用这份文档（以及一条刻意的约定）

| 你想做的事 | 看哪一节 |
| --- | --- |
| 第一次读代码，想知道从哪进 | §1、§2 |
| 追一个具体现象（断言没生效 / 变量取不到 / 报告缺记录） | §3 的对应链路 + §7 的防线清单 |
| 加一个新断言算子 / 新协议 step | §6、§8 |
| 用 AI 旁路包（`haify`）/ 想知道它的模块职责 | §2.2 |
| 改文档时怕写漂 | §十 |

> **NOTICE：本文档只写「模块与函数」，不写行号。**
> 本仓的其它文档（缺陷修复日志、能力清单）大量引用 `response.py:394` 这类行号 —— 那是
> **事后记录**，写在当时是准确的。但架构文档会被反复翻阅、且每次改动都可能让它过期：
> 行号会在**每一次无关改动**后漂移（本批 7 处修复就让 `make.py` 的行号整体后移了 60 余行），
> 而 `module.py::function()` 这种写法只有**函数被改名/删除**时才需要更新 —— 后者是**语义变化**，
> 前者只是噪声。维护成本因此从「每改一行都要改文档」降到「改了 API 才改文档」。
> 护栏：`tests/docs_consistency_test.py::TestArchitectureDocCoversEveryModule` 会检查
> **每个包内模块都被本文档提到**（§2.1 内核 + §2.2 AI 旁路包，**新增模块忘了写文档会变红**），
> 因此本文档不会因为「新增了一个模块」而悄悄过期。
> ★**§2.2 的判据按"那一节的切片"判**，不是查全文：两个包有同名模块（`cli.py` / `__init__.py`），
> 查全文会让 AI 旁路包漏掉的模块被内核那张表**蒙过去**（假绿）。

## 一、一句话模型：**两段式**（生成期 / 运行期）

```
                    ┌──────────────── 生成期（不联网、不解析变量）────────────────┐
  YAML/JSON 用例 ──►│ loader 校验 → make 渲染成 *_test.py（链式 API）→ black 格式化 │──► pytest 用例
                    └───────────────────────────────────────────────────────────┘
                                              │
                    ┌──────────────── 运行期（真发请求、真解析变量）──────────────┐
                    │ pytest 收集 *_test.py → InterfaceTester.test_start()       │
                    │   → 逐 step：解析变量 → 发请求 → extract → validate        │
                    │   → StepResult / TestCaseSummary → 报告与日志              │
                    └───────────────────────────────────────────────────────────┘
```

三条必须记住的推论（它们解释了这个框架绝大多数「看起来奇怪」的设计）：

1. **生成期不解析 `${...}`**。`make.py` 不 import `parser`，YAML 里的 `$var` / `${func()}`
   原样作为**字符串字面量**落进生成物，运行期才由 `parser` 解析。
   → 所以「`hmake` 通过」**不等于**「变量写得对」；变量名拼错只在运行期暴露。
2. **生成的 `*_test.py` 是「另一种写法的用例」，不是中间产物**。它和手写 Python API 用例
   走**完全同一条**运行链路（都构造 `TStep`、都由 `IStep` 实现类执行）。
   → 所以「YAML 能做的」与「Python API 能做的」在运行期是同一件事，两条入口的差异只在生成器。
3. **`hrun` = `hmake` + `pytest`**。`hrun` 先转换、再调用 `pytest.main()`，
   两者在**同一个进程**里顺序执行（`cli.main_run`）。
   → 所以「`hmake` 的报错」与「pytest 的报错」格式不同，但都出自这一次命令。

### 2.2 AI 旁路包 `interfacetester_ai/`

> 而它曾经**没有任何文档、也没有任何护栏**——接手的人只能去读 352KB 的方案文档，且"文档漏了模块"**不会有人发现**。

## 三、五条主链路

### 3.1 加载链：文件 → 模型对象

```
loader.load_test_file(path)                     # 按扩展名分派：JSON / YAML(SafeLoader)
  └─ loader.load_testcase(dict)                 # ← 也可被 Python API 直接调用
       ├─ loader.warn_unknown_testcase_fields() # 未知字段告警（config/step/request 三张白名单）
       └─ models.TestCase.model_validate()      # pydantic v2：这里是**唯一**的格式权威
```

要点：

- **模型是唯一权威**：YAML 里能写什么，由 `models.py` 的 `TConfig`/`TStep`/`TRequest` 决定；
  三张 `KNOWN_*_FIELDS` 白名单只用于**告警**，不用于放行/拦截（`loader.py` 只 `logger.warning`）。
- **未知字段只告警不报错**：因为历史用例里存在 v2/v3 残留写法；
  真正「模型认了、生成器却表达不出来」的字段由生成期闸门报错（见 §7 第 3 条）。
- 单数钩子（`setup_hook`）会被**静默丢弃**（生成器只认复数 `setup_hooks`），
  所以 `loader` 对这两个名字有一条专门的 hint 告警 —— 这是「最容易造成假通过」的坑之一。

### 3.2 生成链：模型对象 → pytest 代码

```
make.main_make(paths)                        # hmake / hrun 的入口；逐个路径
  └─ make.__make(path)                       # 目录 → loader.load_folder_files 展开
       ├─ compat.ensure_testcase_v4_api()    # v2/v3 单 api 文件 → v4 testcase
       ├─ make._fail_or_skip()               # 「像用例但不合法」记失败 / 「不像用例」只跳过
       └─ make.make_testcase(testcase)       # ← 核心
            ├─ ensure_generatable_config()          # config 级闸门
            ├─ ensure_generatable_teststeps()       # step 级：模型认但生成器无分支 → 报错
            ├─ compat.ensure_testcase_v4()          # v2/v3 → v4
            ├─ loader.load_testcase()               # 再过一次模型（生成期也做完整校验）
            ├─ ensure_known_comparators()           # 算子白名单 + 形态闸门
            ├─ ensure_json_schema_not_inline()      # 内联 schema 拦截
            ├─ ensure_xsd_files_exist()             # XSD 路径存在性拦截
            ├─ convert_testcase_path()              # 源路径 → *_test.py 路径 + 类名
            │    └─ ensure_file_abs_path_valid()
            │         └─ normalize_module_segment() # 路径段归一（唯一规则，见 §7 第 11 条）
            ├─ make_teststep_chain_style()          # 每个 step → 链式 API 字符串
            │    └─ ensure_python_literal()         # 值 → Python 字面量（唯一漏斗）
            ├─ jinja2 模板渲染 __TEMPLATE__ → 写盘
            ├─ __ensure_testcase_module()           # 需要时写 __init__.py
            └─ format_pytest_with_black()           # subprocess 调 black（带超时）
```

生成物的形状（模板 `__TEMPLATE__`）：

```python
# NOTE: Generated By InterfaceTester 4.3.5
# FROM: <源用例绝对路径>
import pytest                                   # 仅在有 skip 标记时需要
from interfacetester import Config, Step, RunRequest, RunTestCase, Parameters

class TestCaseLogin(InterfaceTester):           # 类名 = 文件名 title case 去掉 `_`
    @pytest.mark.skip(...)                      # 仅 config.skip 时
    def test_start(self):                       # ← pytest 靠这个名字发现用例
        config = (
            Config("登录").base_url("...").variables(**{...}).export(*[...])
        )
        teststeps = [
            Step(
                RunRequest("登录并断言")
                    .with_variables(**{})
                    .post("/login")
                    .with_json({...})
                    .extract().with_jmespath("body.data.token", "token")
                    .validate().assert_equal("status_code", 200)
            ),
        ]
        self.config = config
        self.teststeps = teststeps
        self.test_start()                       # 调 runner 的 test_start
```

要点：

- **类名与文件名由 `normalize_module_segment` 派生**：数字开头的段补 `T`，
  `空格/./-` 折成 `_`。这条规则同时被 `cli.main_convert` 的写盘冲突护栏复用
  （见 §7 第 11 条）——**34 个已入库生成物的名字由它逐字节决定**，
  所以它是「改了就要批量改生成物」的那类函数（有专门的反向护栏）。
- **引用用例**（`testcase:`）会递归生成被引用用例，并在文件头插入 `import`（必要时加 `sys.path` 引导）；
  循环引用在生成期被检测并报错。
- **生成期不解析变量**，只做**可生成性**校验：算子名、schema 引用形式、XSD 存在性、
  引用环、生成物撞名。

### 3.3 执行链：pytest → 请求 → 断言

```
pytest.main(args)                              # cli.main_run 的最后一步（同进程）
  └─ 收集 TestCaseXxx.test_start               # 名字以 test_ 开头，因此被 pytest 发现
       └─ runner.InterfaceTester.test_start()
            ├─ _setup_runner()                 # 建 session/parser、绑项目根、准备日志 sink
            ├─ __parse_config()                # 解析 config.variables / name / base_url / timeout
            ├─ with loader.use_run_root_dir():  # 本用例的项目根作用域（断言期路径解析依赖它）
            │    └─ 逐个 step: runner.__run_step(step)
            │         ├─ 重试循环：仅对 ValidationFailure 重试（retry_times/retry_interval）
            │         ├─ step.run(runner)      # IStep 实现 → 下面那条
            │         └─ 失败时 __record_failed_step()（把失败 step 记进报告）
            └─ finally: 关 db/thrift 连接、归还日志 sink
```

单个 HTTP step 的内部（`step_request.run_step_request`）：

```
1. runner.merge_step_variables(step.variables)      # step 变量 > 上一步 extract > config 变量
2. ext.uploader.prepare_upload_step()               # 规划 upload 字段（files/multipart）
3. parser.parse_variables_mapping()                 # 解析变量之间的依赖（含循环依赖报错）
4. parser.parse_data(request_dict)                  # 解析 $var / ${func()} / ${ENV()} / x_path
5. 组 headers（X-Path 编码、伪头过滤、Request-ID、OAuth2 Bearer 注入）
6. 调 setup_hooks（可拿到 request）
7. build_url(config.base_url, url) + verify/timeout/网络参数的落回与清洗
8. client.HttpSession.request(method, url, **kwargs)
     ├─ 默认 timeout=120s（或 INTERFACETESTER_TIMEOUT）、默认 stream=True（为了取 socket 地址）
     ├─ 网络异常 → status_code=0 的**假响应**（保留请求参数便于排查）
     ├─ 请求**构造**阶段异常（InvalidHeader 等）→ 直接抛 ParamsError（**不**降级成 status 0）
     └─ get_req_resp_record()：请求/响应记录的唯一构造点（同时做**脱敏**）
9. ResponseObject(resp, parser)
10. 调 teardown_hooks（可拿到 request/response）
11. resp_obj.extract(step.extract) → 导出变量（取不到时告警）
12. resp_obj.validate(step.validators) → 断言（失败抛 ValidationFailure，见 §6）
```

### 3.4 汇总与报告链

```
runner.get_summary()                    # pytest 的 session 结束后（或 --save-tests 的 conftest fixture）
  ├─ 逐个 StepResult.success 汇总 + __failed 标记（「抛过异常」这个事实也参与）
  ├─ mask_sensitive_variables()         # 展示副本脱敏（**运行期值不受影响**）
  └─ TestCaseSummary
       ├─ .run.log          # loguru sink 按 case_id 写 logs/{case_id}.run.log（引用用例共用父 sink，refcount）
       ├─ summary.json      # --save-tests：compat._generate_conftest_for_summary 生成的 fixture 写盘
       ├─ report.html       # pytest-html（--html --self-contained-html）
       ├─ junit.xml         # pytest 的 --junitxml（CI 聚合）
       └─ Allure            # 装了 allure-pytest 时自动挂 step 与日志附件
```

`--save-tests` 的机制值得单独记一笔：它由 **`compat._generate_conftest_for_summary()` 生成一个
`conftest.py`**（session 级 autouse fixture，在 teardown 里遍历 `request.node.items` 取 `get_summary()`
写 `summary.json`）。生成前会判首行 marker：**不是我们生成的文件绝不覆盖**（用户的 conftest 是神圣的），
冲突时把内容落到 `conftest.py.interfacetester-new` 并 `exit 1`。

### 3.5 导入链：外部资产 → 标准 YAML（`hconvert`）

```
cli.main_convert(args)
  ├─ 按 --from 选适配器（converters.IMPLEMENTED_SOURCES）
  ├─ convert_*  →  IRCase / IRStep         # 解析 + **sanitize_case（唯一脱敏收口）**
  ├─ cli 三层写盘冲突护栏                   # .yml 名 / schema 名 / 生成物模块名
  ├─ emit_yaml.emit_case()                  # IR → YAML 文件 + schemas/*.json
  └─ emit_yaml.validate_emitted_case()      # 「导出即验证」：load_testcase + make_testcase 干跑 + compile
```

**关键设计**：导入器**不碰运行内核**，只产出标准 YAML，然后复用 §3.2 的生成链。
因此「手写用例能用的东西」导入器也都支持，反之亦然。
`validate_emitted_case` 刻意**不走 `main_make`**（后者失败会 `sys.exit(1)`，把原因吞成一句 "exit 1"）。

## 四、数据模型（对象图）

```
TestCase ──┬─ config: TConfig ──┬─ name / base_url / verify / timeout
           │                    ├─ variables / parameters / export
           │                    ├─ thrift: TConfigThrift（psm/env/cluster/…）
           │                    ├─ db: TConfigDB（MySQL 连接）
           │                    └─ oauth2: TOAuth2（Client Credentials）
           └─ teststeps: [TStep]
                ├─ name / variables / export
                ├─ request: TRequest（method/url/params/headers/cookies/json/data/upload/…）
                ├─ testcase: Callable        # 引用用例（生成物里是 import 进来的类）
                ├─ extract: {变量名: jmespath 表达式}
                ├─ validators: [{算子: [检查项, 期望值, 消息]}]   # YAML 里写 `validate`
                ├─ setup_hooks / teardown_hooks
                ├─ retry_times / retry_interval
                ├─ sql_request: TSqlRequest
                └─ thrift_request: TThriftRequest

运行结果：
StepResult ─┬─ name / step_type / success / elapsed / content_size / export_vars
            └─ data: SessionData（单个请求）或 [StepResult]（引用用例）
                 └─ SessionData ─┬─ req_resps: [ReqRespData{request: RequestData, response: ResponseData}]
                                 ├─ stat: RequestStat（耗时/体积）

```

`IStep` 是运行期的**唯一抽象**：`name()` / `type()` / `struct()` / `run(runner)`。
`Step` 只是它的外壳；`RunRequest`、`RunTestCase`、`RunSqlRequest`、`RunThriftRequest` 是链式构造器，
`StepRequestValidation` 等是**链式中间态**（`.extract()` / `.validate()` 返回的对象）。

## 五、变量、函数与 `${}` 的解析时机

| 写法 | 含义 | 解析时机 |
| --- | --- | --- |
| `$var` / `${var}` | 变量 | 运行期（`parser.parse_string`） |
| `${func(...)}` | 调函数（项目 `debugtalk.py` 优先） | 运行期 |
| `${ENV(NAME)}` | 读环境变量 | 运行期 |
| `${parameterize(x.csv)}` | 读 CSV 做参数化 | **生成物的 import 期**（`Parameters(...)` 是模块级代码） |
| `$$` | 转义成一个字面 `$` | 运行期（优先级高于 `$var`） |
| `header: {value: "${f('a')}"}` | **不支持**（函数参数不允许引号） | 不会被解析，只**告警** |

函数查找顺序（`parser.get_mapping_function`）：
`项目 debugtalk.py` → `parameterize/P`、`environ/ENV`、`multipart_encoder/…` 等特例 →
`builtin/functions.py` 的内置函数 → **Python 内置（仅白名单内）**。

变量优先级（`runner.merge_step_variables`）：
**step 变量 > 上一步 extract 出来的变量 > config 变量**。

两条与安全/健壮性相关的硬约束：

1. **插值里的 Python 内置是白名单制**（`parser.ALLOWED_BUILTINS_IN_INTERPOLATION`）：
   只放开「纯计算 / 类型构造 / 序列工具」。`eval`/`exec`/`open`/`getattr`/`__import__` 等一律拒绝，
   报错里给出两条出路（写进 `debugtalk.py`，或显式设 `INTERFACETESTER_ALLOW_ALL_BUILTINS=1`）。
   修复前 `getattr(builtins, name)` 全开放：从导入的 Postman 集合里可以一路走到代码执行。
2. **变量依赖环不会挂死进程**：`parser.parse_variables_mapping` 用**有限轮数**收敛，
   未收敛时抛 `ParamsError` 并指出未解析的变量名（修复前是 `while` 死循环）。

## 六、断言与算子分发

```
response.ResponseObject.validate(validators, variables)
  ├─ uniform_validator(v)                       # 兼容两种写法：
  │    ├─ {算子: [检查项, 期望值, 消息]}          #   推荐（YAML 里写 validate）
  │    └─ {check, comparator/assert, expect, msg}#   v2/v3 老写法
  ├─ get_uniform_comparator(名)                  # 别名归一：eq/equals/equal、len_eq/length_equal…
  ├─ 检查项取值：resp_obj._search_jmespath(表达式)
  ├─ parser.get_mapping_function(算子名, allow_builtins=False)   # ← 只认两类实现
  │    ├─ ① 项目 debugtalk.py 里的自定义算子（签名 (check_value, expect_value, message="")）
  │    └─ ② 框架内置 22 个算子（builtin/comparators.py）
  ├─ assert_func(check_value, expect_value, message)
  ├─ AssertionError  → 记为 failed（信息含 check_item/check_value/期望值/类型）
  └─ TypeError（仅「操作数类型不匹配」这一族）→ 也记为 failed，并补可操作 hint
```

**检查项可以用的前缀**（`ResponseObject._search_jmespath` 的 `resp_obj_meta`）：

| 前缀 | 含义 | 备注 |
| --- | --- | --- |
| `status_code` | HTTP 状态码 | |
| `headers` / `cookies` | 响应头 / Cookie | |
| `body` | 响应体 | JSON 时是 `dict/list`；**非 JSON 时是 `bytes`** |
| `text` | 已解码的响应文本 | 非 JSON 响应断字符串用它 |
| `elapsed_ms` / `elapsed_s` | 耗时（数值） | `elapsed` 是 `timedelta`，不能直接比大小 |
| `response_size` | **已读到**的响应体字节数 | 与日志里的 `response_length` 口径不同 |
| `reason` | HTTP reason phrase | |

前缀按**前导标识符精确匹配**（`bodyx` 不会命中 `body`），前缀不在表里且不是 `requests.Response`
的属性名时直接报 `ParamsError`（**不会**「自比较」出假通过）。

22 个内置算子：`equal`、`greater_than`、`less_than`、`greater_or_equals`、`less_or_equals`、
`not_equal`、`string_equals`、`length_equal`、`length_greater_than`、`length_greater_or_equals`、
`length_less_than`、`length_less_or_equals`、`contains`、`contained_by`、`type_match`、`regex_match`、
`startswith`、`endswith`、`jsonschema_match`、`xpath_match`、`xpath_count`、`xml_schema_match`。

- 前 18 个是基础算子；`jsonschema_match` 需要 `jsonschema`（主依赖）；
- `xpath_match` / `xpath_count` / `xml_schema_match` 需要可选 extra `xml`（lxml）。
  **缺依赖时抛 `RuntimeError` 并给出安装提示**（不是断言失败），并指出零依赖退路
  （`examples/soap/debugtalk.py` 的项目级算子）。
- 生成期的白名单来自 `make.BUILTIN_COMPARATOR_NAMES`（**从 `comparators.py` 的公开函数动态派生**，
  按字母序）。注意：「第 N 个算子」这个编号按**源文件里的定义顺序**，与那份字母序元组不是同一个序。

## 七、防线清单：「假通过」为主体，外加一条「假失败」

这是本框架最核心的一条设计主线：**宁可响亮报错，也不要「绿了但什么都没校验」**。

- **假通过**（第 1~22 条）：用例绿了，实际什么都没校验 —— 这是本框架最忌讳的，
  因为它把「没测」伪装成「测过了」；

## 九、常见误解（每条都对着一个真实的坑）

| 误解 | 事实 |
| --- | --- |
| 「`hmake` 通过 = 用例没问题」 | 生成期**不解析变量**，变量名/函数名写错只在运行期报 |
| 「YAML 里写 `setup_hook` 和写 `setup_hooks` 一样」 | 只认**复数**；单数会被静默丢弃、钩子根本不执行（`loader` 有专门告警） |
| 「`elapsed` 可以直接和数字比大小」 | `elapsed` 是 `timedelta`，请用 `elapsed_ms` / `elapsed_s` |
| 「非 JSON 响应也能写 `body.xxx` 取值」 | `body` 是 `bytes`；按路径取值会**报错**，请用 `text` 前缀或 XPath 算子 |
| 「`contains` 能断任何响应体」 | 作用在 `bytes` 上会抛 `TypeError`（现在会被转成可读的 failed 并给 hint） |
| 「报告里的 `export_vars` 就是下游拿到的值」 | 报告里的是**脱敏展示副本**；运行期传递用的是未脱敏真值（两条通道刻意分开） |
| 「算子名写错只会在运行时才发现」 | 生成期就报（白名单来自内置算子 + 项目 `debugtalk.py`） |
| 「`hconvert` 生成的用例可以直接跑」 | 断言与骨架值是**尽力而为**：curl 不生成断言、录制/契约造出来的值（时间戳/UUID/id）需要人工替换，导入器会逐条告警 |
| 「`--deselect` 写错了 pytest 会提醒」 | **不会**：不存在的去选 id 既不报错也不警告（批次 9-1 实测），所以有 §7 第 20 条护栏 |

## 十、维护这份文档的约定

1. **新增/删除包内模块** → 必须同步 **§2.1（内核 `interfacetester/`）或 §2.2（AI 旁路包 `interfacetester_ai/`）** 的表
