## 一、一句话结论

**缺陷真实、严重、可复现**——但根因**不是**"反引号/必填词表盲区"，而是
**"文档 → 用例"缺少分段与归属模型**（一个文档只取**第一个**端点，却把**全篇**字段表挂上去）。
这正好落在第二档 **WP2.1 / WP2.3（端点分段 + 字段归属）** 的范围内，**前提已满足**：

## 二、★烟枪级证据：产物本身把材料拼错了

`haify gen --assertions-only 统一文件服务平台-接入应用接口文档.md`（临时工作区实测）：

```
config: name: _oauth2_token
teststeps:
- request: {method: POST, url: /oauth2/token}      ← 认证接口
  validate:
  - type_match: body.path = str                     ← 来自「2.1 创建目录」
  - type_match: body.sourceDirName = str            ← 来自「2.2 更新目录」
  - type_match: body.targetDirName = str            ← 来自「2.2 更新目录」
  - type_match: body.path = str                     ← 重复（同名跨表）
  - type_match: body.path = str
  - type_match: body.path = str
  - less_or_equals: body.files = 10                 ← 来自「3.1 文件上传」的"最多上传 10 个"
  - type_match: body.fileName = str
```

- 端点 `/oauth2/token`（认证）**不会返回** `path`/`sourceDirName`/`files` → 这条用例**跑起来必然失败**；
- 它**通过了全部闸门**，质量状态 `static_valid` → **静静产出一个"看起来正常"的产物**
  （本仓最忌讳的形态：不是响亮报错，而是材料错位）；
- 产出 **1 条**用例，而文档有 **18 个接口 / 92 条人工用例**。

## 四、★修正一处粗糙判定（测量方法学教训）

第一版脚本把"文档里标 `否` 的字段集合 ∩ 被断言的字段集合"当作**误报**，报出 `filename` 一例。
**逐行取证后判定：不是误报**——文档里叫 `filename` 的行有 **7 条**（4 条 `是` + 3 条 `否`），
推出的 4 条断言**引用句与行号都指向标 `是` 的那一行**（702/791/881/955）。
真正的问题是**跨接口同名字段共用一个 `body.filename` 路径**（4 个接口的断言挤在同一路径上）。

> **教训**：**名字级交叉 ≠ 语义级判定**。判"误报"必须回到**行号与引用句**（本仓 T28 的取证方式），
> 否则会把"归属缺失"误报成"推错了"——而两者的处置完全不同。

## 五、结论（修订版）

1. **第二档的正当理由是成立的**（不再是"防漂移"这种软理由）：真实文档上，当前通路产的产物
   **与真实接口不相干**（端点取错、断言跨接口混装），且**不报错**（`static_valid`）。
2. **范围要说准**（避免期待落空）：
   - ✅ 能解决：**端点分段识别**（含表格形态）→ **字段按接口归属** → 每接口一条、断言不串台；
   - ❌ **不解决**：**负例/边界覆盖**（人工 92 条里大量是"错 client_id / 缺参数 / 超限"）、
     **响应字段缺必填列**时的纪律取舍（"存在性 vs 类型"，需产品判断）、**一接口多条用例**
     （人工 92 条 ≠ 17 个接口）。
3. **建议见 §七**（已按 §六 的原型结果重排）。
4. **测量纪律（本备忘踩过的三次坑，都写进了正文）**：
   ① 只比"名字集合"会把归属问题误报成"推错了"（§四）；
   ② 同一坑第二次：`body.path` ×15 是**正常的**（§六）；
   ③ 比两个数字前先确认**坐标系统一**（片内相对 vs 全篇绝对，§六）。

### ★三个新发现（都可复跑）

1. **模型通路没有"整篇取第一个端点"那个结构性缺陷**——它按片送模型，18 条产物的端点
   **全部落在某个接口段上**。所以 ① 的必要性**只针对 `--assertions-only`** ✓（我补的正是在那里）。
2. **交叉引用散文会把模型带偏**：父段 `## 5. 元数据服务接口` 的片里只有一句
   `…文件重命名接口（\`POST /api/metadata/rename\`）见 [3.5 …]` → 模型照它给出
   `url=/api/metadata/rename`、**0 断言** → 被 **S3 拒**（没进产物）✓ 但这是一条**真实的形态风险**：
   **父段片会被误当接口片**（确定性通路靠"表格优先"避开了它）。
3. **模型在"全反引号 + 表格端点"的真实文档上，引用质量明显下降**：
   原始 75 条断言里 **30 条被 T28 拦下（40%）**，而同一模型在 15 份 golden 上是 **0 降级**。
   → 这是"**评测集形态 ≠ 真实文档形态**"在**模型通路**上的量化证据，且它把
   **第二档 WP2.2（证据绑定）的价值抬高了**：当前最大的质量损失点就在这里（45/75）。

> 附：`T3_5_文件重命名` 原始 **2** → 最终 **3**（**多了 1 条**）——那是 **C-2 的确定性映射补充**
> 在起作用（只补不覆盖）✓。

2. **第二档 WP2.2 证据绑定**——**实测把它的价值抬高了**（模型通路 40% 降级率 = 最大的质量损失点）；

   **16 → 15**。→ 探针改成**自己写 UTF-8 文件**，stdout 只打 ASCII 摘要。
2. **扁平片 vs 标题跨度差一行**：`split_document` 的片不含尾随空行（21-45）而标题跨度到 21-46 →
   "整节被片包住"会把**本节自己的窗口**判成"别的接口"→ 拒绝绑定。改为"**头行落在片内**"。
3. **绑定窗口太宽**：绑到整张字段表后，③ 限定词检查会拿**同表里别的字段**的类型判 `qualifier-conflict`
   （假红）→ 窗口**窄化到承载该事实的那一行**。
4. **`type_match: number` 会被 S7 拒**（`number` 不是合法类型名）—— 真实文档的字段表就写 `number`，
   §九 那轮的 "S7×1" 失败正是它。✅ **2026-09-26 已修**：`assembler.normalize_type_match()`
   把**无歧义别名**归一（`string`→`str`、`字符串`→`str`），把**有歧义**的（`number`/`数字`）
   摘下来交人工（`unknowns` 里 `type-name-unusable`）而**用例照常产出**（一条断言的**名字**
   不该把整条用例打死 —— 覆盖率就是这么丢的）。详见 `docs/未做完的待决策项.md` §9.11。

## 上传路径（§9.26）:真发文件 vs 只给文件名

```powershell

```

探针自己在临时工作区里拉起 mock（夹具文档把限额缩到 1KB），跑**两条真用例**：

| 用例形态 | 请求里有没有"大小" | 结果 |
| --- | --- | --- |
| `upload: {files: <2KB 文件>}` | **有**（multipart 部件大小） | mock **命中**大小规则 → **用例通过（1 passed）** ✓ |
| `params: {files: @big.zip}`（T3_1 的形态） | **没有** | **未命中** → 用例失败 ✓（**服务端判不了**，不是用例错） |

★这两条就是"上传类负例步骤能不能被验证"的分水岭：**事实在不在请求里**，
与"模型提示词写得好不好"无关。

★三条**容易误判**的坑（都已写进脚本/代码注释）：

① `haify run` 被 **L3 闸门**拒（`l3_refused`）是**有意**的保险——真发请求必须显式
`INTERFACETESTER_AI_SANDBOX=on`；脚本已代做，并把**拒因**打出来（否则只看到退出码 2，
会误判成"用例跑挂了"）。
② 归属闸门的**粒度必须是"节"**：按整篇、按祖先节、或让文档标题里的"统一"命中公共节，
三种写法都会让闸门**形同虚设**（实测 `body.path` 被别的接口的响应示例救活两次）。
③ **判不了就不判**：引用句在文档里定位不到 → 放行；反过来"挑最短匹配节"会**误摘**
（`请求体` 这种标题多处都有）。误摘比漏摘更坏——T10 的误伤率审计守的就是这个。
