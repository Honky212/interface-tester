## 认证方式（环境前提，不是待测接口）

所有接口都要在请求头里带 OAuth2.0 的 Bearer Token：

1. 用平台分配的 `client_id` / `client_secret` 换取 Token（OAuth2.0 的 client_credentials 模式）；
2. 换取地址由平台部署方给出（测试环境是「基础地址 + `/oauth2/token`」，请求体为
   `application/x-www-form-urlencoded`：`grant_type=client_credentials` + `client_id` + `client_secret`）；
3. 把返回的 `access_token` 放进每个请求的 `Authorization` 头，形如 `Bearer {access_token}`；
4. 返回里的 `expires_in`（文档示例值 `3600` 秒）是有效期，过期需重新换取。

> ★**这一节刻意不写「方法 + 路径」的端点形态**：它描述的是**环境前提**，不是待测接口。
> 写了端点形态，工具会把它当成一个接口片去生成用例（示例文档 §3 第 12 行）。
> 本文件与原文定位一致：**只对「创建目录」一个接口生成用例**。

## 公共请求头

| 头 | 必填 | 说明 |
| --- | --- | --- |
| Authorization | 是 | OAuth2.0 的 Bearer Token：`Bearer {access_token}` |
| X-Path | 是 | 安全校验头：本次请求要操作的路径，服务端用它做权限校验 |

> ★**首列写「头」**（不是「字段」）：这样它不会被当成请求体字段表，工具也就**不会**产出
> "断言请求头"这种取不到值的断言（示例文档 §3 第 15 行）。
> **注意**：`X-Path` 值必须与请求参数中的 `path` 字段完全一致，否则会返回 `FILE_1018` 错误。
> 唯一例外是**创建目录**：其 `path`（新目录路径）只需以 `X-Path` 开头即可（`X-Path` 是父目录路径）。

## 公共响应格式

所有接口的响应体统一是 `FileResult` 信封：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| success | boolean | 是 | **固定值**：成功响应 `true`，失败响应 `false` |
| errorCode | 可空 | 是 | **固定值**：成功响应 `null`；失败响应是错误码字符串（见「公共错误码表」） |
| message | string | 是 | 提示文案，**易变**：不要按值断言，只断类型 |
| data | 可空 | 是 | 业务数据容器：**创建目录成功时为 `null`**；其它接口的结构见各自接口节 |

统一返回示例：

```json
{"success": true, "errorCode": null, "message": "操作成功", "data": null}
```

> ★**为什么「类型」列写「可空」而不是 `string` / `object`**：原文写的是「业务错误码，
> 成功时为 `null`」「返回的业务数据，失败时为 `null`」——若类型列写 `string` / `object`，
> 就与成功响应里的 `null` **自相矛盾**，体检闸 D2 会**拒整份文档**（示例文档 §3 第 4 行，实测）。
> 「可空」是原文口径的忠实写法，而且**判据并不因此变软**：成功响应示例里的 `null` 会直接变成
> `equal` 断言（`body.errorCode == null`、`body.data == null`）——跑得绿才说明文档没写错。

## POST /api/directory/create （创建目录）

创建新的目录。实现位置：`DirectoryController.java`（原文 2.1）。

> ★标题形态：**方法名在标题最前**，中文名**隔一个空格**放在路径之后（示例文档 §1 第 2 行）。
> 编号挡在方法名前、或中文名紧贴路径，都会出事（实测：后者会被并进 URL → 请求 404）。

#### 请求头

| 头 | 必填 | 说明 |
| --- | --- | --- |
| Authorization | 是 | `Bearer {access_token}` |
| X-Path | 是 | 父目录路径（示例 `/app1/`）：新目录的 `path` 必须以它开头 |
| Content-Type | 是 | `application/json`（原文的调用示例里有这个头） |

#### 请求体（JSON）

| 字段 | 类型 | 必填 | 说明 | 示例值 |
| --- | --- | --- | --- | --- |
| path | string | 是 | 新目录的完整路径。**约束**：必须以 `/` 开头、必须以 `/` 结尾、不能包含连续的 `//`、不能等于 `/`、目录名称开头和结尾不能有空格、必须以请求头 `X-Path` 中的路径开头 | `/app1/documents/reports/` |

请求体示例：

```json
{"path": "/app1/documents/reports/"}
```

> ★**约束写在「说明」列里**：`说明` / `取值` / `允许值` / `约束` 四种列头等价（示例文档 §1 第 6 行）。
> ★**请求侧字段不会被断言**（内核只把响应侧当断言对象）——这张表的价值在**模型通路**：
> 模型会照它把请求体写进 `json`（`--assertions-only` 的产物只出 `method` + `url`，是已知缺口）。

#### 成功响应

```json
{"success": true, "errorCode": null, "message": "操作成功", "data": null}
```

响应说明（**响应侧字段的出处**，`body.<字段>` 的归属靠它）：

- `success`：布尔，**固定值** `true`（创建成功）
- `errorCode`：成功时为 `null`（固定）
- `message`：文案易变——只断类型，不按值断言
- `data`：**固定值** `null`（创建目录不返回业务数据）

> ★`data` 是 `null` **不是缺陷**：原文 2.1 的成功响应就是这么写的。这个接口"光看文档"能确定的
> 断言就是信封这四条（附录 D 有逐条实测），**不要再往里编** `dirPath` 之类原文没有的字段——
> 那正是"模型幻觉"的入口。

#### 失败响应

```json
{"success": false, "errorCode": "FILE_4001", "message": "目录名称必须以/开头并以/结尾", "data": null}
```

> ★失败响应要靠**非法请求**才触发：工具**明确跳过**失败响应示例，不把它塞进正常用例，
> 并把这件事写进 `unknowns` 让你看见（示例文档 §1 第 11 行）——负例该**单列步骤**。

#### 业务规则

**正常路径**：

- 创建成功：HTTP `200`，响应体 `success=true`、`data=null`
  （依据：原文 2.1 的成功响应 + 《统一文件服务平台-接口测试用例-测试1》TC-DIR-001「返回200，success=true」）
- 允许创建多级嵌套目录：`path` 形如 `/app1/level1/level2/level3/`（依据：TC-DIR-002）

**非法请求才触发的分支**（每条都标依据；**负例该单列步骤**）：

- `path` 不以 `/` 开头、或不以 `/` 结尾：失败响应 `errorCode: FILE_4001`（HTTP `500`，依据 TC-DIR-003 / TC-DIR-004）
- `path` 含连续的 `//`：失败响应 `errorCode: FILE_4003`（HTTP `500`，依据 TC-DIR-005）
- `path` 等于 `/`：失败响应提示路径格式错误（HTTP `500`，依据 TC-DIR-006）——原文未给准确错误码，见附录 E 第 1 条
- 目录名称开头和结尾不能有空格（`FILE_4018`）：违反时失败响应返回该错误码（依据：原文 2.1「路径格式要求」）
- 缺少 `path` 参数、或请求体为空：失败响应 `errorCode: FILE_1010`（「目录路径不能为空」，依据原文 1.5 + TC-DIR-009/010）——HTTP 状态码原文未写死，见附录 E 第 2 条
- `path` 不以请求头 `X-Path` 中的路径开头（`FILE_1018` 路径与Header不一致）：失败响应返回该错误码（依据：原文 1.3 的注解；与测试用例文档的口径差异另见附录 E 第 3 条）
- 目标目录已存在：TC-DIR-008 写「返回 `200`（幂等）**或** `500`（提示已存在）」——二义，见附录 E 第 4 条

> ★**状态码一律写 3 位数**（`200` / `500` / `403`）：写全了 `status_code` 才判得动（示例文档 §1 第 15 行）。
> ★**没写清的分支一律进附录 E、不产断言**：含糊处不会变成幻觉，只会变成待办——这就是
> "能确定的确定下来，不能确定的响亮点名，判不了就不判"。

curl -X POST https://unifsp.cernet.com/api/directory/create \

  -H "X-Path: /app1/" \
  -H "Content-Type: application/json" \

## 附录 C 常见问题（原文照录；**其中 Q2~Q6 涉及别的接口，本文件不为其产用例**）

**Q1: X-Path 是什么？为什么需要它？**

A: `X-Path` 是一个安全校验头，用于验证请求的路径与实际操作的路径是否一致，防止越权访问。
请求头中的 `X-Path` 必须与请求参数中的 `path` 字段完全相同。

**Q2: 预览链接为什么有时效和次数限制？**

A: 预览链接是临时访问凭证，设置时效（2小时）和次数（3次）限制是为了安全性考虑，
防止链接泄露后被滥用。

**Q3: 上传同名文件会发生什么？**

A: 系统会自动覆盖原文件，并创建历史版本记录，原文件内容可以通过版本管理接口找回。

**Q4: getList 与 getInfolist 接口有何区别？**

A: `getList` 返回精简的版本信息（版本号、大小、MD5、生成时间），适合前端列表展示；
`getInfolist` 额外返回文件名、后缀、所属目录等详细信息，适合需要展示文件/目录上下文的场景。

**Q5: 版本回滚后，原当前版本会丢失吗？**

A: 不会。回滚操作不会删除原当前版本，而是将目标历史版本的内容置为新的当前版本，
原当前版本转为历史版本，仍可通过版本列表接口查询和再次回滚。

**Q6: 元数据查询接口 list、query、queryPage 有何区别？**

A: 三者区别如下：

- `list`：仅查询当前目录下的文件，不含子目录，返回脱敏 VO
- `query`：递归查询当前目录及所有子目录，返回脱敏 VO 并额外携带 `dirPath`（文件所在目录路径）
- `queryPage`：递归查询并支持分页，返回 MyBatis-Plus `IPage` 结构，`records` 为 `FileMetadataVo` 对象（含 `dirPath`）

## 附录 E 原文没写清、因此**不产断言**的点（逐条点名）

> 这一节是**产物的一部分**：含糊处不会变成幻觉，只会变成待办。要让它们变成断言，先让文档把话说全。

1. **`path` 等于 `/` 的准确错误码**：原文只写「路径格式错误」（TC-DIR-006 的预期结果是「返回500，提示路径格式错误」），没有给码 → 不产断言。
2. **缺 `path` 参数 / 空请求体的 HTTP 状态码**：原文 1.5 只给了 `errorCode: FILE_1010`；测试用例文档写「`400` 或 `500`」→ 二义 → 只产错误码断言、不产状态码断言。
