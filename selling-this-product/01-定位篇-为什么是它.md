# 为什么是 InterfaceTester：把「用例写得快」和「结果可信」同时做到

> **目标读者**：测试负责人 / 测试开发 / 架构师
> **一句话主张**：写 YAML 就能跑接口测试，而且**它不允许用例"绿了但什么都没校验"**。
> **发布建议**：技术公众号首篇、内部推广第一封邮件、技术评审开场材料

---

## 一、接口自动化的三种现状，你大概占了其中一种

| 现状 | 症状 |
| --- | --- |
| **A. 手写代码脚本** | 一个接口一段 `requests` + `assert`，半年后没人敢改；环境切换靠改代码；报告要自己拼 |
| **B. 工具点出来**（Postman / Apifox 等） | 单接口好用，**链路用例**（登录拿 token → 带 token 下载 → 删除）勉强；**进 CI 卡**；用例是"点"出来的，评审时看不清 |
| **C. 已经有框架** | 用例能跑，但**跑绿了不代表测过了**——断言写漏、字段名拼错、参数化数据集是空的，全都静默通过 |

InterfaceTester 针对的是**第三种痛**：接口测试最贵的不是"能不能发请求"，而是**结果能不能信**。

---

## 二、它不是又一个新框架，而是把"工程化"做到底的 HttpRunner 分支

- 内核 `interfacetester` **5.0.1**，是 [HttpRunner](https://github.com/httprunner/httprunner) **v4.3.5 的二次开发分支**（Apache-2.0，附 NOTICE，符合上游许可要求）；
- 因此 HTTP 全方法、`extract` + jmespath、`config.parameters` 数据驱动、`testcase` 用例复用、hooks、OAuth2 这些**你已经熟悉的写法全部照旧**，迁移成本≈抄一遍 YAML；
- 在此基础上做了三件事：**系统化的"防假通过"改造**、**22 个内置断言算子**、**AI 协作层（把接口文档变成用例草稿）**。

---

## 三、三个关键设计取舍（也是它的护城河）

### 1. 两段式：生成期 / 运行期彻底分开

```
生成期（不联网、不解析变量）  YAML ──校验──▶ 渲染成 *_test.py（链式 API）──black──▶ pytest 用例
运行期（真发请求、真解析变量）  pytest 收集 ──▶ 解析变量 ──▶ 发请求 ──▶ extract ──▶ validate ──▶ 报告
```

**这条设计带来三个直接好处**：

1. **产物是标准 pytest 用例**，不是黑盒——IDE 能跳转、能打断点、能 `-k` 筛选、能和公司现有 pytest 资产混跑；
2. **YAML 能做的和 Python API 能做的是同一件事**（走完全相同的执行链），不用在两套语义之间反复对照；
3. **`hrun` = `hmake` + `pytest`**，一条命令完成"转换 + 运行 + 报告"，CI 里也只需要一条命令。

### 2. 变量与函数机制足以覆盖企业级签名场景

`$var`、`${func()}`、`${ENV(NAME)}`、`${parameterize(x.csv)}`，其中 `${func()}` 调的是**项目里自己的 `debugtalk.py`**：

```python
# debugtalk.py —— 项目自己的函数库，YAML 毫不知情地调用它
def sign(params: dict, secret: str) -> str:
    import hashlib, urllib.parse
    raw = urllib.parse.urlencode(sorted(params.items())) + secret
    return hashlib.md5(raw.encode()).hexdigest()
```

```yaml
# 用例里直接用：MD5 签名、HMAC、AES/SM2、动态造数、时间戳……都在这里落地
headers:
  X-Sign: ${sign($payload, ${ENV(API_SECRET)})}
```

**这意味着 90% 的"框架不支持"其实不用改框架**——加断言算子也只是在 `debugtalk.py` 里写一个 `(check_value, expect_value, message="")` 签名的函数。

### 3. 宁可响亮报错，也不要"假通过"

这是全仓最核心的一条纪律，也是它和多数框架最大的差别：

- **生成期闸门**：断言算子名拼错、`validate` 形态非法、内联 JSON Schema、XSD 路径不存在 —— 在**转换阶段**就报错退出（退出码 1），根本不让它跑起来；
- **运行期不静默**：字段名写错取不到值 → 告警；非 JSON 响应上写 `body.xxx` → 直接报错并告诉你改成 `text` 或 XPath；
- **断言里的 Python 内置走白名单**：`${eval(...)}`、`${getattr(...)}` 这类插值被拒绝（有显式逃生口），从导入的 Postman 集合里"一路走到代码执行"这条路被堵死。

> 不是"我们希望它别出问题"，而是**把每一种曾经出过问题的形态，都做成有人守着的闸门**。详见第 03 篇。

## 四、谁应该用它

| 适用 | 说明 |
| --- | --- |
| 有接口文档 / 存量 Postman / HAR 录制，想把测试资产**沉淀成可进 CI 的用例** | `hconvert` 一键导入（第 05 篇） |
| 测试人员写 YAML、开发人员写 `debugtalk.py`，**分工清晰** | 这是它设计的工作模式 |
| 已有 pytest 体系，需要**一个接口层**与之共存 | 产物就是 pytest 用例 |
| 存量 SOAP/XML 老系统需要结构化断言 | 内置 `xpath_match` / `xpath_count` / `xml_schema_match`（第 02 篇 §3.10） |
| 想让 AI 帮忙写用例，但**不敢让 AI 直接改 CI** | `haify` 只产草稿，**人工转正才进 `cases/`**（第 04 篇） |

## 五、什么场景**不要**选它（先说清楚）

- **性能压测**、**UI 自动化**、**移动端原生**：不在范围内，属于别的工具；
- **并发治理 / 测试数据管理 / 多机报告聚合**：按设计属于框架之外，需要另行投入；
- **gRPC / WebSocket / MQ / 私有 TCP**：不支持，需要改框架；
- **Thrift**：内置但**实验性且未验证**（Windows 上不可用）；
- **期望"任意自然语言文档 → 无人工审核自动进 CI"**：明确**不承诺**，见第 04 篇的承诺边界。
