# 它最值钱的部分：不让你「假通过」

> **目标读者**：测试负责人（最痛的点）、质量管理者、技术评审
> **一句话主张**：接口用例最大的风险不是"跑不通"，而是**跑绿了却没测到东西**。我们把这个仓库最重的投入放在了这里。
> **发布建议**：技术深度长文、内部分享压轴、评审时的"为什么值得选它"答辩材料

---

## 一、先说一个反常识的事实

**"用例绿了" 和 "接口测过了"，是两件事。**

下面这些情况，用例都会**绿**：

| 你可能干过 | 结果 |
| --- | --- |
| 断言字段名拼错 | jmespath 取到 `None`，`not_equal: [x, ""]` **通过** |
| YAML 里写了两段 `validate:` | **后者胜、前者静默丢弃** → 那段里"故意写错的断言"整体蒸发，`hrun` 报 **1 passed** |
| 参数化数据集是空的（CSV 只有表头） | pytest 判 **skip**，`hrun` **exit 0**、零告警 |
| 断言算子名拼错，且恰好是个 Python 内置 | 静默通过 |
| 写了个框架"认但生成器没分支"的字段 | 字段连同断言一起消失 |
| 用例其实失败了 | `summary.json` 里 `success: true`，失败步骤不进 `records` |

这不是耸人听闻——**上面每一条都是这个仓库真实踩过、修过、并且留了回归用例的**。

## 二、防线清单（逐条登记到第 57 条）：谁拦、哪个用例守着

仓库里有一份**逐条登记**的清单：曾经造成假通过（以及少数假失败）的具体形态 → 现在由谁拦 → 由哪个用例守着。

挑几条最具代表性的：

| 曾经的失效形态 | 现在谁拦 | 效果 |
| --- | --- | --- |
| 单数 `setup_hook` 被静默丢弃 | `loader` 专门给出这条 hint 告警 | 你会**看见**它被丢了 |
| YAML 重复键（如两段 `validate:`） | **加载层**判重报错，**点名键名 + 两处行号** | 那个"静默蒸发一段断言"的洞被堵死 |
| 参数化数据集为空 | **响亮报错**，点名"哪个参数、取值来源是什么" | 不再静默 skip + exit 0 |
| 算子名拼错，且是 Python 内置（如 `print`） | **生成期**白名单拦下 | `hmake` 阶段报错 + 退出码 1 |
| `validate_script` 这类"模型认、生成器无分支"字段 | 生成期 `ensure_generatable_teststeps` | 命中即报错，不再静默消失 |
| 检查项写成 `$response.status_code` | 报错**带你的原文** + 正确写法 | 不再是"内存地址 + Python 栈" |
| 非 JSON 响应上写 `body.code` | 直接报错并给 `text` / XPath 改法 | 不再静默得到 `None` |
| 请求**构造阶段**就失败（如 header 值不是字符串） | 抛 `ParamsError` 并说明"请求一次都没发出去，这不是网络问题" | 不再伪装成 `status_code: 0` 的假响应 |
| 用例失败但 summary 说成功 | 两个"事实来源"都参与汇总 | 报告不再说谎 |
| 凭据明文进日志/报告 | 统一脱敏（请求侧 + 响应侧 + URL userinfo） | `Authorization` / `password` / `token` / `Cookie` → `******` |

完整清单在 `docs/架构与调用链.md` §七（57 行表格，逐条给"谁拦 + 回归用例名"）。

## 三、生成期闸门：把问题挡在"跑起来"之前

**这是最容易被忽略、却最省钱的一层**：很多问题在"转换"阶段就能精确判定，不必等运行期。

```python
# 生成期会拦下并报错（退出码 1，且不产出 *_test.py）：
#   1. 断言算子名拼错 / 写法非法（带用例、步骤、原文定位）
#   2. 内联 JSON Schema（含 $schema/$ref —— 会被当变量解析）
#   3. XSD 文件路径不存在 / 内联 XSD 字符串
#   4. "模型认了但生成器没有分支"的字段
#   5. 两个用例撞同一个生成物文件名 / 引用环
```

**现场可复现的演示**（本材料写作时已在仓库内**现场复现**，30 秒可验）：

```powershell
# ① 算子名拼错 → 报错 + 退出码 1 + 不生成 *_test.py
python -m interfacetester make demo.yml      # validate: - equall: [status_code, 200]
#   实测输出：
#   FunctionNotFound: unknown assert comparator: equall
#   自定义断言算子请定义在项目 debugtalk.py 里，签名 (check_value, expect_value, message="")
#   内置断言算子（22 个）: contained_by, contains, endswith, equal, ... xpath_match
#   → EXITCODE=1，且 bad_test.py **不存在**

# ② 换成 Python 内置名 print → 同样被拦（这正是"静默通过"的高发形态）
#   实测输出：FunctionNotFound: 'print' 是 **Python 内置函数**，不能作为断言算子。
#   → EXITCODE=1，且 bad2_test.py **不存在**
```

**报错质量本身就是功能**：会告诉你是哪个用例、哪个步骤、原文长什么样、内置算子有哪 22 个、自定义算子的签名该怎么写。

## 四、运行期不静默：能判定的绝不放过，判不了的**响亮告警**

有些事**运行期原理上判定不了**，框架的处理方式是——**明确告警，而不是假装没事**：

| 场景 | 为什么判不了 | 框架怎么做 |
| --- | --- | --- |
| `not_equal: [body.x, ""]`（想表达"存在且非空"） | jmespath 对"字段缺失"和"值为 null"都返回 `None`，无法区分；硬判失败会破坏 `eq: [body.x, null]` 这种合法写法 | **告警**，且放过明确期望 `null` 的两写法 |
| 数值算子两侧都是字符串（`"9" > "100"` 为真） | 字典序比较是 Python 语义，无法断言用户意图 | **告警** |

**而能判定的，一律判成"可读的失败"**：类型不匹配导致的 `TypeError`（如 `elapsed` 是 `timedelta`、`bytes` 对上 `str`）会转成**带检查项/实际值/期望值/hint 的断言失败**，而不是一行 pytest error；但**不掩盖算子自身的 bug**（非类型类的 `TypeError` 照旧抛出）。

## 五、这套纪律是怎么被守住的

三条机制保证它不会随版本退化：

1. **每个修复都配一条回归用例**（仓库里 74 个 `*_test.py`，连 `conftest.py` 与 mock 共 76 个测试文件；2026-09-27 本机全量：**2545 passed / 121 skipped / 6 deselected / 2672 collected / 1826 subtests / 0 failed**）；
2. **"注入验证"**：把修复注掉，护栏必须**立刻变红**——做不到就说明护栏是假的（仓库里连"护栏自己打偏"的两次失误都留了痕）；
3. **元护栏**：连"文档有没有覆盖每个模块""退出码表与代码常量是否一致""探针脚本是否都被例行任务收录"都有自动化判据。

> 一句可以直接引用的话：**这个仓库不是"我们希望它可靠"，而是"每一种出过问题的形态，都有人守着"。**

## 六、为什么这对你（采购方/负责人）是钱

| 假通过的代价 | 这套设计带来的变化 |
| --- | --- |
| 上线后才发现问题 → 修复成本是测试期的 10 倍以上 | 断言漏洞在**写用例/转换**阶段就被拦 |
| "用例全绿"却不敢发版 → 测试形同虚设 | 绿灯有**依据**（每条断言都在报告里留了结果） |
| 新人写的用例看不出来有没有测到东西 | 生成期闸门 + 告警 + 报告明细，**评审有抓手** |
| 排查"到底测没测"花掉半天 | 每条用例一份 `.run.log`（DEBUG 级请求/响应/断言明细） |
